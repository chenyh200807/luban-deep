# 内核算子 · 试验日志

**为什么存在**:三个算子(L1 内核)不是靠"听起来对"立住的,是靠**能不能提前拦住错误方案**。
本文件记录每次真实使用,**包括预测错的那些**——错的那些往往最能说明算子的真实边界。

**纪律**:预测必须在调研**之前**写下,否则是事后诸葛亮,不计入。

## 试验 #2 · 2026-07-26 · 数据库事务与锁层(前瞻使用)

**性质**:真前瞻。四个预测在做任何新调研之前写下,只基于上一轮 SQLite 专家报告的背景。

### 预测与验证对照

| # | 算子 | 预测(查之前) | 验证结果 |
|---|---|---|---|
| P1 | 一 | workers=2 下「同步阻塞起 admission control」失效,BUSY 会发生 | ✅ **证实且更严重**——10/11 库 `busy_timeout=0`(SQLite 默认值,零等待) |
| P2 | 一 | `delete` 模式库读被写阻塞 | ✅ 成立(7 个库根本没设 `journal_mode`) |
| P3 | 二 | BUSY 会留痕,**可推导** | ❌ **被证伪**——`bi_service` 大量 `except Exception` 吞掉 `OperationalError` |
| P4 | 三 | 改 WAL 前必须先确认文件系统类型 | ✅ ext4 本地块设备,WAL 安全,阻塞解除 |

### 算子表现

**算子一(不可约束缚)——最强的一次。**
仅凭「SQLite 写锁是 per-file 跨进程」这条不可约束缚 + 新事实「生产 `UVICORN_WORKERS=2`」,
**在零新调研的情况下推翻了一份高质量专家报告的核心结论**。该报告的「BUSY 不可能发生」
有一个未被写出的隐含前提:单进程。

**算子二(可推导性)——预测错了,但正因为错才证明了价值。**
它预测「可推导」,验证发现「结构上不可推导」。但**它的使命在提问时就完成了**:
因为先问了「这个答案能从手上推出来吗」,才没有去翻生产日志(那会是一次注定白费的调查),
并直接指向正确动作——**改前向埋点,而不是回溯**。

> **这是算子区别于规则的关键:规则告诉你撞过的墙在哪,算子告诉你这堵墙能不能撞穿。**

**算子三(未声明保证)——成功,价值中等。** 正确指出 WAL 的隐藏契约(共享内存依赖 →
网络文件系统会损坏),验证后解除阻塞。

### 顺带炸出的问题(算子的副产品)——**含一条我自己搞错的**

| 问题 | 证据 | 状态 |
|---|---|---|
| ~~10/11 库 `busy_timeout=0`~~ | ~~只有 `sqlite_store.py` 设了~~ | ❌ **已证伪,见下** |
| `bi_service` 用 `except Exception` 吞 BUSY | ≥10 处,**静默失败零日志** | ✅ 成立 |

### 自我证伪记录:我用 grep 推断了一个运行时值

**我做的**:`rg -c 'busy_timeout'` 发现只有 1 个文件有这个字符串 → 推断其余 10 个库是 0
(C API 的默认值)→ 结论「并发写零容忍」。

**实测**:

```
sqlite3.connect(path)  不传 timeout  →  PRAGMA busy_timeout = 5000 ms
```

**Python `sqlite3` 模块的默认 `timeout` 是 5.0 秒**,底层就是 `busy_timeout`。
所有库实际都有 5 秒等待(`member_console/service.py:2533` 是 2 秒,更短但非零)。
**我的结论错了。**

**错在哪(这才是要记的)**:我跳过了**语言/框架默认值**这一层。
grep 只能回答「代码里有没有显式写」,回答不了「运行时实际是多少」。
**这正是算子二该抓的**——「我要的答案能从手上的东西推出来吗?」答案是**不能**,
而我没问就推了。

**已回写 L2 嗅觉库**:删掉错误的那条,替换为
「用 `grep 有没有写 X` 推断运行时 X 的值 → 跳过了默认值层 → 实测一次」。
这条比原来那条通用得多,适用于任何语言的任何默认参数。

> **进化协议第一次真实触发,触发者是本 skill 的作者。** 这正是反向查表要抓的形态:
> 故障发生 → 回查 skill → 「有这一条,但这一条本身是错的」→ 修 L2。
