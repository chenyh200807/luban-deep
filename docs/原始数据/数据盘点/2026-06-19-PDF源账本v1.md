# PDF 源账本 v1

- **日期**: 2026-06-19
- **目标**: 把 `docs/原始数据/PDF` 下的 PDF 原件逐文件建账，让 AI 能知道每个 PDF 是否已有结构化派生、还缺什么、下一步该进哪个 compiler。
- **产物**: `docs/原始数据/数据盘点/extractions/pdf_source_ledger_v1/`
- **状态**: `raw_pdf_evidence_ledger`，不是 runtime supply，不是 official score authority，不写 LearnerState / GBrain / production registry。

## 结论先行

PDF 还没有全部编译完成，但现在已经不是“笼统知道有 95 个 PDF”的状态，而是 **95 个 PDF 全部有逐文件账本**。

当前账本结论:

| 指标 | 数量 |
|---|---:|
| PDF 原件 | 95 |
| PDF 体量 | 4,386,216,862 bytes |
| 候选结构化派生引用 | 39 |
| 仍需编译或映射 | 56 |

这一步的意义不是把 PDF 直接接入生产，而是先把 raw evidence authority 立住: PDF 原件负责证明来源，结构化 JSON 负责供 AI 快速读取，二者之间还需要 provenance map 才能进入签发链路。

## AI 第一入口

后续 agent 需要判断 PDF 资产时，优先读:

1. `docs/原始数据/数据盘点/extractions/pdf_source_ledger_v1/manifest.json`
2. `docs/原始数据/数据盘点/extractions/pdf_source_ledger_v1/pdf_sources.jsonl`
3. `docs/原始数据/数据盘点/extractions/pdf_source_ledger_v1/summary.md`

`pdf_sources.jsonl` 中每条记录都有:

- `pdf_id`
- `source_path`
- `category`
- `compilation_status`
- `candidate_structured_derivative_refs`
- `priority`
- `recommended_next_action`
- `file.bytes`
- `file.sha256`
- `runtime_guard`

## 三原则落地

- **Thin wrappers, fat skills**: `build_pdf_source_ledger.py` 只做薄账本: 文件枚举、hash、保守分类、派生状态、下一步动作。真正 OCR、教材切块、标准结构化、讲义解析、题库抽取必须进入后续专门 compiler / skill kernel。
- **First principles**: 当前一等事实是“PDF 原件与结构化派生之间的证据关系”，不是“能否马上给 AI 喂 PDF 全文”。
- **Less is more**: 先做 source ledger，不做 OCR、不做向量库、不写 runtime registry、不制造第二套知识库 authority。

## 诚实边界

- `candidate_structured_derivative_refs_available=39` 不等于已签发 release artifact，只说明当前目录里能找到候选结构化派生入口。
- `needs_compilation_or_mapping=56` 不等于这些 PDF 无价值，只说明它们还没有进入当前结构化 source layer。
- 本账本没有页码级 hash、OCR 质量评分、图片/表格抽取覆盖率。
- 本账本不能作为 official score、LearnerState、GBrain 或 production runtime 写入依据。

## 下一步

最稳的下一步不是立刻 OCR 全部 56 个缺口，而是按优先级做:

1. 先处理 21 个 `P1_compile_or_map`: 标准、教材、讲义、真题。
2. 同步给 39 个候选派生 PDF 补 `PDF -> JSON provenance map`，避免“已有 JSON”但无法回溯原件。
3. 练习/公式/补充资料保持 P2/P3，只有进入具体产品链路时再抽取，避免过度编译。
