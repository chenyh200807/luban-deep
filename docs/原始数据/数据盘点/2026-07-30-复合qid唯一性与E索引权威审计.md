# 复合 qid 唯一性与 E 索引权威审计

- **日期**: 2026-07-30
- **状态**: `read_only_audit`（只读 SQL/REST，零写操作），不是 runtime supply，不是 official score authority
- **提问口径**: tier1 复合键 `{exam_year}::{source_chunk_id}::E{n}` 在 `questions_bank` 里唯一吗？能不能上线？
- **结论一句话**: 前两段（year, chunk）在可建键的 354 行 case 上**零冲突**，但第三段 `E{n}` 在 DB 侧**没有任何列作权威**，编译期 0-based 与运行时 1-based 差一位；模拟建键命中 23/354 且**语义正确 0 条**，全是静默错绑。**tier1 不可上线。**

### 1. pgo bank 键形态：E 索引是必需的第三段

- 1384 条采分点记录，distinct qid = **179**，全部形如 `{year}::{chunk_id}::E{n}`，**0 个畸形**。
- distinct `(exam_year, source_chunk_id)` 对 = **74**。
- 每对下的 E 索引个数分布：`{1个:41对, 2个:3对, 3个:1对, 4个:17对, 5个:11对, 6个:1对}` —— 一对多，所以 E 段不可省。
- 年份覆盖 2015–2025。

### 4. pgo 179 键回查 DB：45 个键在 DB 里没有对应行

按 `(exam_year, source_chunk_id)` 回查 case_study 行：

| 口径 | 唯一命中 | 多行冲突 | 查无此行 |
|---|---:|---:|---:|
| 74 个 (year, chunk) 对 | **64** | **0** | **10** |

10 个"查无此行"的对全部是 2015/2016 的 `EXAM_XW{year}_CASE_{n}` 命名族 —— **DB 里根本没有 2015/2016 的 case 行**。也就是 pgo bank 有 45/179（25%）的采分点键在 DB 侧无宿主，属于纯悬空供给。

### 5. 致命发现：E 索引在 DB 侧无权威（粒度错配 + off-by-one）

**编译期口径**：原始 `FINAL_CLEANED_EXAM_V{year}.json` 中，一个 chunk 的 `exercises[]` 装的是同一道案例的第 1 问…第 N 问；编译器 qid 的 `E{idx}` = **该数组下标（0-based）**。

**DB 侧实况**：

- 64 个命中对，**每对只有 1 行**；与原始 JSON stem 尾部逐字比对结果：**64/64 全部是 raw idx 0（第 1 问）**。
- 兄弟小问（第 2 问…第 N 问）确实存在于 DB，但 **`source_chunk_id` 全为 NULL**。实样：2017 `EXAM_1A434000_P0017_01` 的第 2 问 = id `8744`/`17089`（chunk NULL），第 3 问 = id `8745`/`17087`/`17090`（chunk NULL）。
- 即：**(year, chunk) 之所以"唯一"，是因为兄弟行丢了 chunk_id —— 这是数据缺失造成的假唯一，不是键设计好。**

**运行时口径**：`extract_case_subquestion_items()` 从 stem 文本解析"第N问"，**1-based**。实测 354 行可建键 case 行的运行时 `display_index` 分布：`{'1': 334, '2': 8, '3': 6, '4': 4, '5': 2}` —— **没有 0**。

**模拟运行时建键打 pgo bank**：

| 指标 | 值 |
|---|---:|
| 命中 | **23 / 354** |
| 其中语义正确（运行时 E == 原始 exercise 下标） | **0** |
| 静默 off-by-one 错绑 | **23 / 23（100%）** |

23 条全部是：DB 行真身是第 1 问（bank 里是 `::E0`），运行时建出 `::E1`，命中的是**第 2 问的 rubric**。判分会拿错采分点，**且不会报错**。

### 6. tier1 的理论天花板 = 63 行（17.8%），不是 354

即使把 E 索引口径修正为 0-based，可绑定行数也被数据本身封死：

- 64 个唯一命中对 × 每对 1 行 = 至多 64 行；
- 其中 **1 对的 bank 里根本没有 E0**：2018 `EXAM_1A432000_P0020_02`（DB id `9175`），bank 只有 `E1`；
- 故 **tier1 可正确绑定上限 = 63 行 / 354 可建键 case 行 = 17.8%**，占全部 1961 行 case 的 3.2%。

换句话说：把 off-by-one 修对，tier1 也只是从"23 条全错"变成"63 条对、291 条无键"，**不足以作为判分权威通道**。

### 7. 顺带发现（非 case）：全表同 (year, chunk) 多行只有 3 组，全是选择题

- 2021 `EXAM_1A415041_P0014_02` → 3 行 multi_choice（`12536`/`12537`/`12538`）
- 2021 `EXAM_1A431022_P0013_01` → 2 行 multi_choice（`12533`/`12534`）
- 2021 `EXAM_1A434000_P0022_02` → 2 行（`9444` single_choice / `12617`）

这 3 组已在同日《questions_bank 系统污染盘点》中判定为 **chunk id 分配 bug（三组内各行是不同题）**，不是重复入库。

## 缺口与诚实边界

1. **E 索引没有 DB 权威列**。`questions_bank` 没有 `subquestion_index` 一类的显式小问序号列；运行时靠 stem 文本解析重建，编译期靠数组下标 —— 两套口径没有共同 authority，**任何一侧改解析规则都会静默改判分绑定**。
2. **兄弟小问的 chunk_id 已丢失**，且不可从兄弟行复制（兄弟小问各自有独立 chunk id，抄过去会造成新的错绑）。详见同日清洗计划 B10。
3. **未覆盖**：本审计只验证了 case_study 的 tier1 键；tier2/tier3 匹配通道、以及 pgo bank 采分点内容质量（2026-07-11 异源终审已判定含 A 级判分错误）不在本次口径内。
4. **未逐条复核的残差**：64 对中有 **24 对**的 bank 含 `E1`，而运行时模拟只命中 **23** 条；差的 1 条（2023 `EXAM_1A434000_P0010_02` / id `9502`）推测是运行时未解析出 `display_index=1`，**未逐行复核，记为开口**。
5. **快照时点**：本次读到 total = 4638 行；同日 questions_bank 清洗调查另一次快照读到 4635 行（三行 `12865`/`9035`/`9037` 已删）。两份数字的差异源于快照先后，**不是统计口径分歧**。

## 结论

1. **提问口径（同年同 chunk 多行 case）下键设计没有破洞**：0 组冲突。这一条成立。
2. **真正的破洞在第三段 `E{display_index}`**：DB 里没有任何列作权威，运行时文本解析（1-based）与编译期数组下标（0-based）差 1，且兄弟小问 chunk_id 已丢失。
3. **tier1 复合键当前不可上线**。上线的实际效果是 23 条静默错绑（100% 语义错误），修对 off-by-one 后天花板也只有 63 行（17.8%）。
4. **先决条件**：`questions_bank` 增加显式 `subquestion_index` 列并回源派生 chunk 归属之前，tier1 不应作为判分绑定通道；见同日清洗计划 B10 的三步处置。
