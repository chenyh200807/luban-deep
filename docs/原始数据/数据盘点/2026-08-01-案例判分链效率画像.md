### 1.3 三条对既有结论的重标定

1. **scene 分类器与 followup 分类器在案例判分轮上一次都没跑。**
   2026-06-29 的 Phase-1 复核把 `interpret_question_followup_action` 点名为「真正的首答前阻塞 LLM（占阻塞分类器 ~79%，p99 17–19 s）」。那是**全量 turn** 口径。在**案例判分轮**这个子集上，因为 `active_object` 已存在、走 submission 路径，两个分类器的 gate 都短路。**判分链的时延杠杆里没有分类器这一项。**

2. **`learner_state.refresh` 已不在 turn 关键路径上。** 108/108 轮它在 `turn.runtime` 结束之后才启动。Task 6 时代（2026-06-28）把 7–21 s 的 learner refresh 当阻塞项的前提，在判分链上**已过期**。

3. **M22 基准（v1 判分 LLM p50 2253 ms / ~$0.0005 条）只覆盖 batch judge 一跳。** 今天的 batch judge p50 3.41 s，与 M22 同量级（+51%）。但 M22 完全没有测量 **rubric 推导 22.3 s** 这一跳——它是 6 月后加入的，且现在是判分链**单跳最大延迟项**。用 M22 数字推断今天的判分成本会低估 5–10 倍。

### 1.4 TTFT 与「用户实际在等什么」

这是本次画像最反直觉的一段。

| 指标 | p50 | p95 | n |
|---|---|---|---|
| 第一个 `progress`（understanding） | 0.20 s | 0.20 s | 111 |
| 第一个 `progress`（writing） | 1.12 s | 2.85 s | 111 |
| **第一个 public `content`（TTFT）** | **1.61 s** | 26.7 s | 111 |
| **流内最大单次停顿** | **20.2 s** | **41.8 s** | 111（max 103.8 s） |
| 停顿前已吐字数 | **65 字** | — | |
| 停顿后吐字数 | **3,034 字** | — | |
| 整轮 public 字数 | 3,137 | 5,133 | |
| 流式平均吐字速率 | 76.6 字/s | — | |

**读法**：用户在 1.6 s 看到大约 65 个字的开场白（"好的，我来批改…"级别），然后**屏幕冻结 20.2 s（p50）/ 41.8 s（p95）**，之后 3,034 字判分正文一次性涌出。

- **TTFT ≈ 1.6 s，不由任何 LLM 决定**——它由 turn setup（30 ms）+ 首个 ack 决定。owner 记忆中的「~5.4 s」在本批样本上未复现，可能是别的 turn 类型或早期版本。
- **真正的感知等待 ≈ 22 s（1.6 + 20.2）**，且这段静默**精确对应 rubric 推导（22.3 s p50）+ batch judge** 的窗口。
- 因此：判分链的"慢"在用户端不是"慢慢出字"，而是**开场白之后的一段死寂**。

### 2.3 最大的三个 token 消费者

1. **主 agent LLM prompt：37,898 input token（p50）。** 当它跑的时候是压倒性第一，但**只在 10/114 轮（8.8%）跑**。
2. **rerank 候选集：12,177 input token/轮，100% 的轮都跑。** 计费为 $0（gte-rerank 未计价），延迟仅 0.32 s，所以**不是成本杠杆**，但它是"检索了多少东西"的度量尺。
3. **batch judge：2,020 input + 547 output token/轮**，是判分核心里最大的稳定项。
   - 输出侧第一名是 **rubric 推导 2,152 output token（p50）**，且样本中有 **1 次打满 `max_tokens=8192`**（trace `f8e80cdf...`，该次单调用 **78.6 s**，直接把整轮推到 124 s）。

### 2.4 判分 prompt 里到底塞了什么

**证据块 6000 字上限的真相**：`max_evidence_chars = 6000`（`deeptutor/tutorbot/agent/loop.py:654`，截断在 `:696-697`）**存在，但它在主 agent 的 prompt 上，不在判分链上**。判分 LLM 的 prompt 里**没有 6000 字证据块**。

判分链三个 prompt 的实际组成与硬上限：

| prompt | 组成 | 上限 | 代码 |
|---|---|---|---|
| **batch judge** | 2 行 system + 每个采分点一行 JSON（`采分点` 全文 / `关键词` / `判定标准`）+ 学生作答 | 学生作答 **`[:1500]`**；**采分点文本无截断**（30 个点就是 30 行全文） | `rubric_grader_v1.py:1669`（`_batch_prompt`）、`:1688`（1500 截断）、`:1663`（system） |
| **rubric 抽取** | stem + 参考答案 + ~20 行固定规则 | stem **`[:800]`**、参考答案 **`[:2000]`** | `rubric_grader_v1.py:1889`、`:1896`、`:1899` |
| **rubric 推导** | stem + （可选）KB 证据块 | stem **`[:2000]`**；KB 块 5 条 × **600 字**，标题 40 字 | `rubric_grader_v1.py:2104`、`:2189`、`:2131`、`:2178-2181` |

**判分 prompt 里没有：历史轮、rubric 全文（只有点列表）、教材 chunk（KB 块默认关闭，见 §4）。** 换句话说，判分 prompt 本身是**瘦的**（p50 ~1k token），它慢不是因为 prompt 长——**是因为 output 长（2,152 token）且模型在长 JSON 生成上慢**。这一条推翻了"塞太多东西进 prompt"的直觉假设。

## 3. 三档模式（智能 / 深度 / 快速）对比

### 3.1 路由事实

- 枚举 `TutorBotResponseMode = Literal["smart","fast","deep"]`，默认 `"smart"`（`deeptutor/tutorbot/response_mode.py:7,34`）。
- **smart 遇到结构化作答提交 → 解析成 `fast`**（`response_mode.py:207`，`_looks_like_structured_submission_followup`）。所以「智能档交案例作答」实际走 fast 策略。
- **fast 不绕开判分。** 两个入口都在 mode 分支之前无条件执行 V1 判分：
  - `deeptutor/tutorbot/agent/loop.py:4655` `_run_case_grading_direct` 在 `:4788` 的 `if response_mode == "fast"` **之前** await。
  - `deeptutor/capabilities/deep_question.py:5238` `_grade_case_rubric_v1` 无条件执行。
- **判分被强制锁在主模型上**：`deeptutor/capabilities/tutorbot.py:1039-1058` —— 当 `question_lifecycle_scene ∈ {mcq_grading, case_grading}` 时 `fast_preferred_model` 被清空，fast 档的轻模型优待对判分**不生效**。
- fast 唯一真正省掉的 LLM 是 legacy MCQ 解释器（`deep_question.py:1178-1179`，`_should_use_deterministic_grading_feedback` 仅在 fast 生效），**且只对已知 `correct_answer` 的客观题生效，案例题永远不满足条件**（`:1184-1200`）。
- fast 还把 `max_tool_rounds` 从 4 降到 1、`latency_budget_ms` 从 20000 降到 6000（`response_mode.py:307-330`）——这影响主 agent 循环，不影响判分链。

### 3.2 实测（诚实标注：fast 样本量不足）

| 日期 | mode | n | e2e p50 | e2e p95 | input p50 | output p50 | 调用/轮 | $/轮(均) |
|---|---|---|---|---|---|---|---|---|
| 07-30 | deep | 83 | 37.7 s | 67.8 s | 4,561 | 1,477 | 5 | $0.0074 |
| 07-30 | fast | **1** | 29.6 s | — | 8,599 | 2,383 | 3 | $0.0129 |
| 07-31 | deep | 23 | 32.5 s | 59.5 s | 6,548 | 781 | 6 | $0.0262 |
| 07-31 | fast | **2** | 55.9 s | 62.1 s | 43,412 | 2,962 | 5.5 | $0.0488 |

> **`smart` 档在本批 106+3 轮里一次都没有作为 `selected_mode` 落地**——全部被解析成 `deep` 或 `fast`。
> **fast 档总样本 n=3，不足以下任何结论。** 三档时延/token 差异**本次未能测出**，登记为缺口。

### 3.3 学生体验（快速档）

从代码路径看：快速档学生**仍然要等完整判分链**（rubric + judge），拿到的仍是完整判分正文。fast 省的是 tool 轮数和 MCQ 解释，案例题上**几乎没有体感差别**。这与「快速档=更快」的产品承诺不一致，是一个待裁决的产品口径问题（本报告不提方案）。

### 4.2 KB 溯源"取证据"——当前 0 成本，因为默认关闭

`_fetch_stem_kb_evidence`（`deep_question.py:2321`，`rag_search(intent="case_rubric_derivation")`，`asyncio.wait_for(timeout=8.0)`，`limit=5`）会往 rubric 推导 prompt 里塞 5×600 字 KB 块。**但它被 `LUBAN_STEM_RUBRIC_KB_GROUNDING` 门控，默认 OFF**（`deep_question.py:2306`）。

**若开启此 flag，预计每轮 +1 次 RAG（约 6 s）+ 约 3.2k 字进 prompt（≈ +1,600 token）。这是一个尚未支付的税，登记备查。**

### 4.3 唯一有量级的新增税：OD-004 submission-text stem fallback

- commit `dc21b2a5f`（07-31），代码 `deep_question.py:2589-2618`；配套 `c590081eb`（形状判定下沉到 `case_output_policy.py:280` 的本地正则）、`64bdff836`（`loop.py:1812-1819` ctx 侧）。

- 104/114 轮（**91.2%**）**没有任何主 agent LLM 调用**，但其中 101 轮照样跑完了 RAG 检索（均值 6.26 s）+ 85 次 rerank（12,177 token）。
- RAG 产出的证据块（`max_evidence_chars=6000`，`loop.py:654`）**只喂给主 agent prompt**；判分 prompt 不含 KB（§2.4），KB 取证据 flag 默认关（§4.2）。
- turn_events 侧佐证：public `sources` 事件**只在 9/111 轮**出现——即 102/111 轮学生连引用来源都没看到。
- **量级：每轮约 6.3 s（p50）+ 56~124 次 Supabase 往返 + 12k rerank token，产物无下游消费者。**
- ⚠️ **诚实边界**：本结论由遥测反推（"无消费者 span"），我**没有**逐行读完 `_maybe_prefetch_grounded_rag` 的所有下游消费点。落地任何优化前必须先补一次代码层确认——不排除 RAG 结果被某个未插桩的确定性渲染路径使用。

### W2 —— rubric 缓存 36% 的"该命中未命中"【强】

| 指标 | 值 |
|---|---|
| 窗口内 rubric LLM 调用总数 | **94** |
| 去重后不同 prompt 数 | **45** |
| 字节完全相同的重复 prompt | **49（52.1%）** |
| **其中距上一次相同调用 < 3600 s（即应当命中缓存）** | **34（36.2%）** |
| 这 34 次消耗的墙钟 | **375.5 s** |

- 缓存实现：`_RUBRIC_EXTRACTION_CACHE: dict[str, tuple[float, list]]`，**模块级进程内 dict**（`rubric_grader_v1.py:56`）；TTL 3600 s（`:58-65`）；容量 512（`:68-76`）；淘汰按**创建顺序**而非 LRU（`:114-116`）；key = sha256(prompt 版本 + kind + model + provider + 参考答案 + stem + kb_digest)（`:78-93`）。
- **根因假说**：生产 `WORKERS=2`（既有结论），每个 worker 各持一份 dict，跨 worker 必然 miss；叠加进程重启（容器今天 `Up 5 hours`）清空。36.2% 的"应命中未命中"与两 worker 均分的理论上限高度吻合。
- **batch judge 完全无缓存**——每次提交都重新付费。
- **缓存命中率插桩为零**：`_get_cached_rubric_points`/`_set_cached_rubric_points`（`:95`/`:109`）没有任何计数器、日志或指标。上面的 36.2% 是我用 prompt 字节哈希**从外部反推**的，不是系统自报的。

### W3 —— rubric 推导的长输出与截断风险

- 推导 output p50 **2,152 token**，是全链最大输出项，且 `max_tokens=8192`。
- 样本中 **1/44 次触顶 8192**（trace `f8e80cdf...`），该次单调用 **78.6 s**，直接决定了那一轮的 124 s。
- 推导是**串行、不可流式向用户展示的中间产物**——它的 22.3 s 全部落进 §1.4 的静默窗口。

### W4 —— Supabase N+1 往返

- 每轮 **56 次（p50）/ 124 次（p95）** `supabase.*` 调用，累计 DB 墙钟 24.8 s（p50，含并行）。
- 124 s 那轮的时间线里可见明确的串行链：`select.questions_bank` **连续 48 次**、`search_questions_bank_text` 27 次，每次 80–300 ms，首尾相接无重叠。
- 单次 `rag.supabase.search` 内部就跑掉 17.0 s（4,430 ms → 21,406 ms）。

### W5 —— 20.2 s 的感知静默（非 token 浪费，是体验浪费）

- 65 字开场白 → **停 20.2 s（p50）/ 41.8 s（p95）** → 3,034 字涌出。
- 这段静默不是"没算完"，而是**算完的中间结果（rubric 点位、已判完的第一组 judge）没有被逐步 emit**。
- 这正是 `docs/plan/题目生命周期与助教运行时/2026-07-29-case-subquestion-map-reduce-sequenced-emit-design.md`（task #10，立项未实施）要解决的问题——本画像为该设计提供了量化依据。

### W6 —— 尾段 15.1 s 完全无观测

- `luban_v1_grading` 事件 → `turn.runtime` 结束之间 **p50 15.1 s / p95 26.8 s**，期间**没有任何 span**（104/111 轮零 span）。
- 从 turn_events 看这段有大量 public content 事件（3,034 字 / 76.6 字每秒 ≈ 40 s 的吐字窗口，与之重叠），所以**大概率是流式渲染 + 落库**，不是 LLM。
- 但**这是推断不是证据**——尾段占整轮 40%，却是观测盲区。

## 8. 诚实边界（本报告没有证明什么）

1. **fast 档 n=3，三档对比不成立。** §3.2 的表格只能读作"deep 档的两日画像"。
2. **smart 档在本批零落地**，无法与另两档对比。
3. **W1（RAG 白烧）是遥测反推**，缺一次代码层的下游消费点确认。这是本报告置信度最低的高价值结论。
4. **修复轮税额未量化**（§4.4）——机制清楚，数字没有。
5. **尾段 15.1 s 的成因是推断**（§5-W6），不是观测。
6. **样本以 QA 军团为主**，题型分布、作答长度分布未必代表真实学生流量。
7. 所有 p95 基于 108~111 个样本，尾部估计不稳；p99 一律未报。
8. **未做 A/B、未做归因实验。** 本报告是描述性画像，任何"改 X 能省 Y"都是候选假说，需按 `eval-design` 单独设计验证。
