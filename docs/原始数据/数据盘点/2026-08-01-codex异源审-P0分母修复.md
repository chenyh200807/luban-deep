# Codex 异源代码审查：P0 案例题覆盖分母/分子修复

审查基线：本地远端跟踪引用 `origin/main=27d9165a308d8dd248b8562af176643bf42a16f0`。`git log` / `git show` 确认 PR #624 的 merge commit 为 `889119c11bd4797ca8f31f002ba0b36bed443064`（核心实现 commit `e6fed928201a73e5855a5185505cb93263101b33`），PR #627 的 merge commit 为 `27d9165a308d8dd248b8562af176643bf42a16f0`（核心实现 commit `8cdbacb35d9dd176dbb74fb811d9d3676167daf1`）。以下结论全部按 `origin/main` 当前源码行号，不以 PR 描述代替代码。

## 1. 修正后是否仍有旁路让"部分覆盖拿整题满分"

### batch 路径 `_grade_case_batch_v1`

**结论：有旁路。** batch 本身确实复用 `_grade_one_case_v1`，并要求所有 case 子项都完成判分后才汇总，避免只汇总成功子项形成假满分；但它只是把原始 item 原样传给单题核，没有为 item 派生 `case_reference_covered_count` / `case_stem_subquestion_count`。`_grade_one_case_v1` 又只在 `_sub_n > 1 and 0 < _cov_n < _sub_n` 时缩放，因此没有这两个字段的 tier-2 batch item 会得到 `_cov_n=0`、`_sub_n=0`，继续把局部参考点池归一到整题名义满分。证据：`deeptutor/capabilities/deep_question.py:2549`、`deeptutor/capabilities/deep_question.py:2557`、`deeptutor/capabilities/deep_question.py:2706`、`deeptutor/capabilities/deep_question.py:2741`。

默认 DeepQuestion batch 构造链也没有补这两个字段：batch builder 只处理答案、旧 score/diagnosis 后交给 adapter；adapter 对每个 item 只附加 `construction_grading_result`，没有运行 TutorBot 的题面标题抽取和采纳集计算。所以上游 item 偶然自带两个字段时可被修正，但当前默认生产构造链没有这一保证。证据：`deeptutor/capabilities/deep_question.py:6099`、`deeptutor/capabilities/deep_question.py:6123`、`deeptutor/services/construction_grading/deep_question_adapter.py:183`、`deeptutor/services/construction_grading/deep_question_adapter.py:212`。

另一个可见性缺口是：batch 父事件只汇总 score/max 并把子事件放进 `items`，没有把任一子事件的 `case_grading_partial_scope` 提升到父事件；因此即使某个子项正确缩放，父事件的顶层范围声明仍丢失。证据：`deeptutor/capabilities/deep_question.py:2752`、`deeptutor/capabilities/deep_question.py:2765`。

### tier-1 / tier-3 分支

**tier-1 结论：有未封堵旁路。** 只要 `load_rubric(qid)` 返回 points，就不会进入包含 #624 覆盖缩放的 `if not points` 分支；tier-1 不读取两个覆盖计数。普通 rubric 判分把采分点分值之和同时作为 `awarded_score` 上限和事件 `max_score`，全部命中即可得到该点池满分。当前只对“rubric 总分与名义满分不一致”发 marker，并未阻断或缩放。因此若 compiled rubric 实际只覆盖整题的一部分、但其点池被配置成整题名义分，仍可拿整题满分。证据：`deeptutor/capabilities/deep_question.py:2492`、`deeptutor/capabilities/deep_question.py:2522`、`deeptutor/capabilities/deep_question.py:2678`、`deeptutor/services/construction_grading/rubric_grader_v1.py:149`、`deeptutor/services/construction_grading/rubric_grader_v1.py:200`。

**tier-3 结论：有“诊断分”层面的受限旁路，不是官方成绩旁路。** 无参考答案时，tier-3 从 stem（或 submission fallback stem）推导点池并直接归一到整题名义满分，不消费覆盖计数；若传入 stem 本身只是整题的一部分、而 `construction_grading_result.max_score` 仍是整题分值，全部命中仍会显示整题诊断满分。代码会把该事件标为 `diagnostic_score=True`、`official_score_allowed=False`，渲染也声明不能作为正式成绩，所以它没有冒充官方成绩，但如果产品红线是“任何用户可见分都不允许部分题面拿整题满分”，此路径仍未关闭。证据：`deeptutor/capabilities/deep_question.py:2560`、`deeptutor/capabilities/deep_question.py:2578`、`deeptutor/capabilities/deep_question.py:2595`、`deeptutor/capabilities/deep_question.py:2617`、`deeptutor/capabilities/deep_question.py:2695`、`deeptutor/services/construction_grading/rubric_grader_v1.py:993`。

### render / stream 是否用另一个 max 覆盖回去

**结论：在已查的 V1 后端可见渲染链中无二次覆盖。** 主 renderer 直接读取同一个事件的 `awarded_score` / `max_score`；score-first stream 和 presentation 也只格式化事件值，没有重算或写回。TutorBot 调用顺序同样把同一个 event 先交 renderer、再交 stream/presentation。因此 #624 写回事件后的 `max_score=整题名义满分` 会以原值显示。证据：`deeptutor/services/construction_grading/rubric_grader_v1.py:788`、`deeptutor/services/construction_grading/rubric_grader_v1.py:793`、`deeptutor/services/construction_grading/rubric_grader_v1.py:993`、`deeptutor/services/construction_grading/rubric_grader_v1.py:1159`、`deeptutor/services/construction_grading/rubric_grader_v1.py:1168`、`deeptutor/services/construction_grading/rubric_grader_v1.py:1237`、`deeptutor/services/construction_grading/rubric_grader_v1.py:1258`、`deeptutor/tutorbot/agent/loop.py:2017`、`deeptutor/tutorbot/agent/loop.py:2032`。

**但存在并行 payload authority 风险，而不是 renderer 覆盖。** DeepQuestion 最终结果仍同时发送未被 V1 改写的 legacy `construction_grading_result` 和包含 V1 GradingEvent 的 `luban_case_rubric_v1`；后端文本使用 V1 event，但任何另行选择 legacy 字段的下游都可能看到另一套 score/max。当前仓库的前端 JS/TS 未检出这两个字段的消费，因此“现有前端会覆盖回去”证据不足，不能断言发生；只能确认双 payload 确实并存。证据：`deeptutor/capabilities/deep_question.py:5469`、`deeptutor/capabilities/deep_question.py:5476`、`deeptutor/capabilities/deep_question.py:5483`、`deeptutor/capabilities/deep_question.py:5492`。

### `derive_outcome_from_event` 的百分比换算

**结论：无独立旁路；它忠实放大上游事件的对或错。** `derive_outcome_from_event` 只取同一事件的 awarded/max，以 `awarded / maximum * 100` 换算，并以 awarded 是否达到 maximum 判断正确；修正后的 `2/10` 会得到 20%，不会重新按局部点池变成 100%。反之，batch、tier-1、tier-3 或标题抽取失败若已经产出错误的整题满分事件，这里也会忠实输出 100%，它没有额外防线。证据：`deeptutor/services/construction_grading/rubric_grader_v1.py:2230`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2240`、`deeptutor/capabilities/deep_question.py:5272`、`deeptutor/capabilities/deep_question.py:5284`。

## 2. 误伤面

### 单小问题目（题面只有 1 问）

**结论：就当前条件判断而言不会被比例缩小，未见误伤。** 缩放条件明确要求 `_sub_n > 1`；题面只抽到 1 问时 `_scope_ratio` 保持 1.0，参考点池仍按整题名义满分归一。标题抽取器按行识别一个合法问题标题时返回单元素 dict，ctx 导出的分母为其长度 1。证据：`deeptutor/capabilities/deep_question.py:2552`、`deeptutor/capabilities/deep_question.py:2557`、`deeptutor/tutorbot/agent/loop.py:1842`、`deeptutor/tutorbot/agent/loop.py:1852`、`deeptutor/services/construction_grading/rubric_grader_v1.py:604`、`deeptutor/services/construction_grading/rubric_grader_v1.py:624`。

### 标题抽取失败（返回 0/1）

**结论：不会造成“错误缩小分数”的误伤，但会造成漏修，允许真实多小问题继续拿整题满分。** wrapper 遇异常直接返回 `{}`；底层抽取只认四类逐行编号格式，空文本或格式不匹配会得到 0，部分识别则可能只得到 1。两种情况都因 `_sub_n > 1` 不成立而关闭缩放。这是保守 fail-open：避免在分母未知时乱扣分，但代价是原 P0 症状仍可复现于未识别题面。证据：`deeptutor/tutorbot/agent/loop.py:91`、`deeptutor/tutorbot/agent/loop.py:100`、`deeptutor/services/construction_grading/rubric_grader_v1.py:589`、`deeptutor/services/construction_grading/rubric_grader_v1.py:624`、`deeptutor/capabilities/deep_question.py:2553`。

### `matched_indexes` 为空但 payload 有值时的回落语义

**结论：不完全正确；只在“确实没有可识别采纳集”时正确，在“已采纳答案但缺 display_index”时会重新放大分子。** 顶层直接匹配一般由 `_own_index()` 给出 display index，最差在有 `correct_answer` 时回 `"1"`，所以该路径不会误回落；无 user stem 时构造器使用所有 covered answers，回落 payload 也与“全部采纳”语义一致。证据：`deeptutor/tutorbot/agent/loop.py:1584`、`deeptutor/tutorbot/agent/loop.py:1602`、`deeptutor/tutorbot/agent/loop.py:1621`、`deeptutor/tutorbot/agent/loop.py:1629`、`deeptutor/tutorbot/agent/loop.py:1753`、`deeptutor/tutorbot/agent/loop.py:1756`。

但逐项匹配路径会在 answer 非空时采纳答案，却只在 child item 自带 `display_index` 时记录 `matched_display_indexes`。若命中的 child 有答案但没有该字段，返回的 reference 非空、`matched_indexes` 却为空；上层随后用 `_adopted or payload.covered_indexes`，把“索引未知”误当成“没有采纳集”，可能再次用检索兄弟行总数充当分子。该空值同时承载两种语义，回落不是完备的。证据：`deeptutor/tutorbot/agent/loop.py:1634`、`deeptutor/tutorbot/agent/loop.py:1648`、`deeptutor/tutorbot/agent/loop.py:1650`、`deeptutor/tutorbot/agent/loop.py:1657`、`deeptutor/tutorbot/agent/loop.py:1831`、`deeptutor/tutorbot/agent/loop.py:1841`。

## 3. max_score 写者收敛

**结论：V1 GradingEvent 链当前有 4 个代码写点、3 个逻辑写者阶段。**

1. leaf 普通 rubric 构造器以采分点和写 `max_score`：`deeptutor/services/construction_grading/rubric_grader_v1.py:194`、`deeptutor/services/construction_grading/rubric_grader_v1.py:205`。
2. leaf PGO coverage 分支是互斥的第二个事件构造写点，以 `official_total` 写 `max_score`：`deeptutor/services/construction_grading/rubric_grader_v1.py:230`、`deeptutor/services/construction_grading/rubric_grader_v1.py:291`。
3. #624 在 leaf 事件已经构造完成后，再由 `_grade_one_case_v1` 对同一事件原地改写一次 `max_score`：`deeptutor/capabilities/deep_question.py:2684`、`deeptutor/capabilities/deep_question.py:2694`。
4. batch 聚合器为新的父事件求和并写一次父级 `max_score`：`deeptutor/capabilities/deep_question.py:2752`、`deeptutor/capabilities/deep_question.py:2765`。

`normalize_points_to_nominal` 只改 rubric point 的 score，不是 GradingEvent `max_score` 写者；它先改变点池总额，随后 leaf 构造器再从点池求 max。证据：`deeptutor/services/construction_grading/rubric_grader_v1.py:2214`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2227`。

**结论：构成 leaf 事件多写者隐患。** 同一个 leaf event 的分母先由 grading kernel 从点池推导，再由 capability 层按 nominal 覆盖；这使 `awarded_score` 与 `max_score` 的共同业务事实跨层完成，未来新增 renderer、writeback 或提前消费 event 时容易读到改写前值。batch 父事件单独聚合本身是合理的事件层级写者，但当前父事件没有同步提升 partial-scope 语义，使 score/max 与范围声明再次分离。证据：`deeptutor/services/construction_grading/rubric_grader_v1.py:2278`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2284`、`deeptutor/capabilities/deep_question.py:2645`、`deeptutor/capabilities/deep_question.py:2694`、`deeptutor/capabilities/deep_question.py:2757`、`deeptutor/capabilities/deep_question.py:2765`。

**建议的单一权威：leaf 的 awarded/max 应收敛到 `rubric_grader_v1.grade_with_rubric` 的事件构造边界；capability 只传入“整题名义满分 + 有效覆盖范围”，不再事后改 event。** 当前统一入口已经在 `grade_with_rubric` 先分派普通/PGO 再构造事件，且所有异步 verdict 最终都经 `_grade_from_verdicts` 回到该入口，这是最窄的既有权威 seam。batch 父事件则保留 `_grade_case_batch_v1` 为父级唯一聚合写者，但必须显式聚合 scope。证据：`deeptutor/services/construction_grading/rubric_grader_v1.py:120`、`deeptutor/services/construction_grading/rubric_grader_v1.py:143`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2268`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2284`、`deeptutor/capabilities/deep_question.py:2706`、`deeptutor/capabilities/deep_question.py:2765`。

此外，DeepQuestion 对外 payload 并列保留 legacy 与 V1 两套 max，不是“同一对象多写”，但属于下游可选择的多 authority：legacy batch max 在 adapter 聚合，V1 event 另行附加。若产品把 V1 作为当前可见判分权威，应在消费合同上明确唯一读者路径，不能让客户端自行二选一。证据：`deeptutor/services/construction_grading/deep_question_adapter.py:203`、`deeptutor/services/construction_grading/deep_question_adapter.py:214`、`deeptutor/capabilities/deep_question.py:5469`、`deeptutor/capabilities/deep_question.py:5492`。

## 4. 结论

**GO-with-changes。** 该 verdict 只表示“#624/#627 的目标单题 tier-2 路径修法成立，可以保留”，不表示 P0 已全链路 CLOSED。

- **保留修复：** 当前 `origin/main` 的单题 TutorBot tier-2 路径确实以“实际采纳集优先、payload 兜底”生成分子，并以学生题面标题数生成分母；在 `0 < c < n` 时把点池缩到 `nominal * c/n`，再把事件分母还原为整题名义满分。`2/10` 经 renderer 和 outcome 仍为 `2/10`、20%，不会被后端显示链改回 100%。证据：`deeptutor/tutorbot/agent/loop.py:1831`、`deeptutor/tutorbot/agent/loop.py:1852`、`deeptutor/capabilities/deep_question.py:2549`、`deeptutor/capabilities/deep_question.py:2557`、`deeptutor/capabilities/deep_question.py:2684`、`deeptutor/capabilities/deep_question.py:2694`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2235`、`deeptutor/services/construction_grading/rubric_grader_v1.py:2240`。
- **必须补 batch：** 默认 batch item 没有覆盖计数派生，仍能绕过该修复；batch 父事件还会丢顶层 partial-scope 声明。通过条件应是 batch 的每个 tier-2 case item 都从其实际采纳参考和学生所见题面得到 c/n，且父事件可表达各子项 scope。证据：`deeptutor/capabilities/deep_question.py:2706`、`deeptutor/capabilities/deep_question.py:2765`、`deeptutor/services/construction_grading/deep_question_adapter.py:183`、`deeptutor/services/construction_grading/deep_question_adapter.py:212`。
- **必须把采纳结果改成三态：** “没有采纳”“采纳但索引未知”“采纳且索引已知”不能继续共用空字符串，否则 payload 回落会在第二种情况下放大分子。通过条件应是 reference 非空但 display index 缺失时 fail-closed/发声，不得自动拿 payload 行数替代采纳数。证据：`deeptutor/tutorbot/agent/loop.py:1640`、`deeptutor/tutorbot/agent/loop.py:1657`、`deeptutor/tutorbot/agent/loop.py:1831`、`deeptutor/tutorbot/agent/loop.py:1841`。
- **必须收敛 leaf max writer：** coverage-adjusted point pool、awarded、whole nominal max 应由 rubric grading kernel 一次性形成 leaf event；`_grade_one_case_v1` 不应再事后改写。batch 只拥有父级聚合 max。证据：`deeptutor/services/construction_grading/rubric_grader_v1.py:194`、`deeptutor/services/construction_grading/rubric_grader_v1.py:205`、`deeptutor/capabilities/deep_question.py:2684`、`deeptutor/capabilities/deep_question.py:2694`、`deeptutor/capabilities/deep_question.py:2752`、`deeptutor/capabilities/deep_question.py:2765`。
- **需 owner 明确 tier-3 红线：** 如果“诊断得分预估 10/10”在部分 stem 上可接受，则当前 `official_score_allowed=False` 的隔离足够；如果红线针对任何用户可见整题满分，tier-3 也必须接入 scope 或在范围未知时不显示硬分。证据：`deeptutor/capabilities/deep_question.py:2560`、`deeptutor/capabilities/deep_question.py:2578`、`deeptutor/capabilities/deep_question.py:2695`、`deeptutor/services/construction_grading/rubric_grader_v1.py:993`、`deeptutor/services/construction_grading/rubric_grader_v1.py:995`。

**证据边界：** 本次按用户要求没有运行测试、没有访问生产、没有复核题述 live 三轮和金标数据；最强证据是 `origin/main` 静态源码与 Git 对象。故结论只到“源码级可达/不可达与 authority 风险”，不把题述 live 结果升级为本次独立验证。

**你没问但我必须说：** `case_grading_partial_scope` 虽已写入事件并导出 metadata，却没有被 renderer 直接消费；用户可见的“仅已覆盖小问”提示来自另一套 `case_subq_coverage_note`，它依赖采分点能否归属到题面标题，归属失败就返回 `None`。因此系统可能分数已正确变成 `2/10`，但页面没有解释这是 `1/4` scope；这不会把 max 改回去，却会造成用户对低分来源的信任损失。证据：`deeptutor/capabilities/deep_question.py:2655`、`deeptutor/capabilities/deep_question.py:2667`、`deeptutor/capabilities/deep_question.py:2693`、`deeptutor/services/construction_grading/rubric_grader_v1.py:671`、`deeptutor/services/construction_grading/rubric_grader_v1.py:681`、`deeptutor/services/construction_grading/rubric_grader_v1.py:844`、`deeptutor/services/construction_grading/rubric_grader_v1.py:845`、`deeptutor/services/construction_grading/rubric_grader_v1.py:1247`、`deeptutor/services/construction_grading/rubric_grader_v1.py:1258`。

层盲区：本次落在判分上下文装配、事件构造和渲染投影层；未覆盖 Supabase `covered_indexes` 生产 SQL/数据质量、真实容器环境变量与前端闭源/仓外消费者。已查仓内 JS/TS 未发现这两个评分 payload 的消费，但这不足以证明所有真实客户端不存在独立选择 legacy max 的逻辑。坏消息是 batch、标题抽取 fail-open、采纳索引缺失三类输入均缺少本次运行证据；其中前两类从静态控制流已能证明保护条件不成立，不能以单题 live PASS 替代。
