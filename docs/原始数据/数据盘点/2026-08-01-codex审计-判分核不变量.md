## 结论先行

1. 存在同一题级分数事实的多写者：grade_with_rubric / _grade_with_pgo_coverage 先产出 awarded_score、max_score，_grade_one_case_v1 随后可再改 event["max_score"]，_grade_case_batch_v1 又在 wrapper 层重新求和产出两字段（rubric_grader_v1.py:194-205,278-291；deep_question.py:2684-2694,2752-2765）。
2. 踩点封顶应在 rubric_grader_v1 的唯一题级 score finalizer 内完成，在 #624 权重缩放之后、事件发布之前执行；不应在 deep_question.py:2680-2681 的 observe-only 装饰层事后补分。
3. 按 #624 当前 target/raw_total 的代码语义，题设数字的最终结果是 8.33 / 20：覆盖后目标空间为 20×2/4=10，原始命中占比为 25/30，缩放后命中 25×10/30=8.33，再封顶 min(8.33,10)=8.33，最后把对外分母还原为 20。
4. 现有 cache 只固定部分 rubric 拆点结果，没有固定同题同答的 verdict/final event；temperature=0 也不是可重复性合同（rubric_grader_v1.py:54-117,1751-1766,2070-2101,2140-2201）。
5. coverage 的 None 目前不是可观测第三态，而被折叠成“不缩放/不显示范围”，效果等于对系统有利的全覆盖。必须改为 single | known | unknown/error 三态。

### 1.4 multiple writers 判定与收敛方案

判定：构成 multiple writers。最硬证据不是“投影很多”，而是同一 event.max_score 先在 rubric_grader_v1.py:194-205 / 278-291 产生，后在 deep_question.py:2684-2694 改写；batch 分数又在 deep_question.py:2752-2758 独立生成。

应收敛到 rubric_grader_v1 内一个唯一 score finalizer：

1. _grade_one_case_v1 只解析 tier、rubric、nominal_full_score 和三态 coverage；tier-2 在此之前完成 #624 权重缩放，但 wrapper 不再改事件分数。
2. 在 _grade_from_verdicts → grade_with_rubric 的现有收敛路径（rubric_grader_v1.py:2268-2284）内，设置唯一 finalize_case_score 语义；只有它可写 awarded_score、max_score、scoring_scope_max。
3. 显式分开 effective_scope_cap=nominal_full×coverage 与 reported_max_score=nominal_full，避免 max_score 同时代表“本次可得上限”和“整题对外分母”。
4. 删除 deep_question.py:2684-2691 的事后 max_score 改写。
5. batch 改由 rubric_grader_v1 的同一 merge/finalizer 聚合 finalized 子事件，保留 child scope/diagnostic/source；deep_question wrapper 只筛选 item 与委托。
6. render、presentation、stream、learning evidence、observability、derive_outcome_from_event 全部只读最终事件。

目标 authority 链：

    tier/coverage authority → rubric 权重缩放 → LLM 只产逐点 verdict
    → rubric_grader_v1 唯一 score finalizer → GradingEvent
    → render/outcome/learning/observability 只读投影

## 2. 踩点封顶方案

### 2.1 层位与执行顺序

封顶应放在 rubric_grader_v1.grade_with_rubric 的题级最终组装点，或它与 _grade_from_verdicts 之间的唯一内部 finalizer；必须在 tier-2 #624 缩放之后、事件发出之前。

证据：

- 逐点 awarded 与题级 sum 现由 grade_with_rubric 计算（rubric_grader_v1.py:149-190），事件也在这里组装（rubric_grader_v1.py:194-205）。
- sync/async batch 都经 _grade_from_verdicts 进入它（rubric_grader_v1.py:2268-2315），这里封顶可覆盖当前所有 verdict 路径。
- #624 在进 grader 前调用 normalize_points_to_nominal（deep_question.py:2546-2557）；该函数用 factor=target/raw_total 线性缩放每个 point.score（rubric_grader_v1.py:2204-2227）。
- deep_question.py:2506-2512 目前只计算超额，deep_question.py:2680-2681 只写 marker。在这个 observe-only wrapper 上改分会延续多写者。

具体顺序：

1. 解析 nominal_full_score。
2. 取得三态 coverage；unknown/error 不得产生无范围数字分。
3. tier-2 先执行 #624：scope_target=nominal_full×covered/total，再调用 normalize_points_to_nominal(points, nominal_total=scope_target)。tier-1 governed rubric 不重写官方逐点权重，但仍必须取得 effective_scope_cap。
4. LLM 只判逐点 hit/partial/miss；prompt 也明确“只判命中不改分值”（rubric_grader_v1.py:1684-1693）。
5. 用缩放后的逐点权重求 sum_awarded_scaled。
6. 再封顶：awarded_score=min(max(sum_awarded_scaled,0), effective_scope_cap)。
7. 同一 finalizer 一次写 awarded_score、对外 max_score=nominal_full、scoring_scope_max=effective_scope_cap 与 coverage marker。
8. batch 只聚合 finalized 子事件；render/outcome 只读。

必须“缩放后封顶”，因为命中和 cap 必须在同一分值坐标系。#624 会改变每个 point.score；用缩放前命中和对比缩放后 cap 会混用单位。

### 2.2 数字验算

题设：

- raw_pool=30
- nominal_full=20
- raw_hit=25
- coverage=2/4=0.5

按 #624 当前实现：

1. 已覆盖范围目标满分：

       scope_target = 20 × 2/4 = 10

2. normalize_points_to_nominal 的缩放因子（rubric_grader_v1.py:2216-2226）：

       factor = scope_target / raw_pool = 10/30 = 1/3

3. 缩放后命中：

       sum_awarded_scaled = 25 × 1/3 = 8.333... ≈ 8.33

   现函数逐点 round 到两位，并把 rounding drift 修到最大 point（rubric_grader_v1.py:2221-2226），具体点分分布可造成最后 0.01 placement 差异；题设比例结果为 8.33。

4. 同坐标封顶：

       awarded_score = min(8.33, scope_target 10) = 8.33

5. #624 对外分母还原整题满分，因此：

       最终 = 8.33 / 20

6. derive_outcome_from_event 的百分比为 round(8.33/20×100)=42（rubric_grader_v1.py:2235-2240）。

若 owner 期待 10/20，则那代表另一条业务规则：“原始命中只乘 coverage、不按 raw pool 归一”，或“命中超过 scope 即满 scope”。这不是 #624 当前 target/raw_total 语义，不能伪装成“只加一个 min”；必须单独裁决。本报告按实际代码给出唯一自洽结果 8.33/20。

## 3. 点池不稳定根源与缓存方案

### 3.1 能与不能确定性化的边界

已经确定性的部分：

- verdict 给定后，grade_with_rubric 按固定规则计算逐点分与总和（rubric_grader_v1.py:149-190）。
- normalize_points_to_nominal 的缩放和 rounding drift 修复是确定性的（rubric_grader_v1.py:2204-2227）。
- 大 rubric 的分组取决于 point count 和已有小问键（rubric_grader_v1.py:1769-1842）。
- batch parser 用短 idx 确定性映射回 point_id（rubric_grader_v1.py:1697-1726）。

不能靠输入规范化/seed 完全确定性化的部分：

1. tier-2/tier-3 点池由 LLM 生成。tier-2 拆点见 rubric_grader_v1.py:2070-2101；tier-3 推导见 rubric_grader_v1.py:2140-2201。这两处没有 seed，也未显式传 temperature=0（rubric_grader_v1.py:2091-2095,2192-2195）。
2. 逐点判定虽传 temperature=0（rubric_grader_v1.py:1729-1766），但源码没有“供应商跨时间/跨版本确定性”合同，也没有可用 seed 的直接证据。temperature=0 只能降低方差。
3. 现有 cache 是单进程 TTL dict：全局存储、默认 3600 秒 TTL 与容量见 rubric_grader_v1.py:54-75,95-117。worker 重启或另一个 worker 会重做 LLM。
4. cache key 包含 prompt version、kind、model、provider、reference/stem、KB digest，但文本只做 strip（rubric_grader_v1.py:78-92）；没有 Unicode NFKC、换行/空白策略版本、bank content hash 或 grader code version。
5. cache 只缓存 rubric points，不缓存同题同答 verdict/event。tier-2 命中缓存后仍会调用 grade_with_batch_judge_async（deep_question.py:2537-2558,2645-2647）。

结论：输入规范化、显式 temperature=0、供应商支持时固定 seed 都只能降方差，不能证明“同题同答必然同分”。

### 3.2 同题同答结果缓存的具体落点

缓存应放在 rubric_grader_v1 内，作为 grade_with_batch_judge_async 前后的唯一 grading-result cache seam；不能放在 render/TutorBot wrapper。当前 LLM 调用点是 deep_question.py:2645-2647，grader 收敛点是 rubric_grader_v1.py:2303-2315。

流程：

1. _grade_one_case_v1 完成 tier、coverage、权重缩放与 authority 过滤后（deep_question.py:2627-2644），把最终有序 points 与 score constraints 交给 cache seam。
2. cache hit 返回不含用户身份的 immutable score facts；当前请求重挂 student_id 与 trace metadata。
3. miss 执行 grade_with_batch_judge_async，通过唯一 finalizer 后，只缓存 event_type=case_grading_completed 且 degraded=False 的事件。完整 verdict gate 见 rubric_grader_v1.py:2256-2265。
4. 事件导出 cache_key_version、created_at、rubric digest、model/provider authority、bank slot/hash、score_authority。

建议 key：

    sha256(
      grading_result_cache.v1
      + qid_or_question_identity
      + normalized_student_answer
      + ordered_rubric_digest(
          point_id,text,policy,required_terms,scaled_score,authority_source
        )
      + nominal_full_score
      + coverage_state_and_effective_scope_cap
      + rubric_provenance
      + bank_slot_and_content_hash
      + extraction_prompt_version
      + adjudication_prompt_version
      + model
      + provider_binding_and_effective_endpoint
      + grader_algorithm_version
    )

文本规范化应做 Unicode NFKC、换行统一、首尾空白去除；不可激进删除会改变答案语义的中间空白。batch key 应 hash 有序子题 cache-key 列表，不能只用 parent qid。

### 3.3 风险清单

1. 稳定错误：cache 只会把第一次随机结果粘住，不会让它更正确。必须先修 coverage/cap/authority，再上结果 cache。
2. 失效不完整：rubric、官答、prompt、model/provider、算法任一变更未进 key，就会复用旧分；TTL 不能代替版本化。
3. 多 worker stampede：现有 dict 是单进程（rubric_grader_v1.py:55,95-117）；跨 worker 需共享存储和 single-flight/幂等写。
4. 隐私：答案可能含个人信息。key 只存 hash，value 去 student_id/session_id/trace_id，并明确租户和保留边界。
5. 规范化过度/hash 错绑：不能把语义不同答案清洗成同一 key；规范化策略本身需版本化。
6. 不得缓存 degraded、exception、coverage unknown，否则短时故障会固化成低分/无分。
7. 官答或人工复核更正需按 rubric/version 精确失效。
8. 首判仍不稳定：cache 解决重复请求漂移，不解决新题首次判分正确性。
9. batch/单题一致性：应缓存 finalized 子题，再组合 aggregate；只缓存一侧会让另一侧重判漂移。
10. 观测歧义：必须区分 cache_hit 与 fresh_adjudication，不能把缓存一致性冒充模型确定性。

## 4. None-即全覆盖的 fail-loud 改法

### 4.1 当前三条静默有利路径

| 路径 | 静态证据 | 实际效果 |
|---|---|---|
| A. 上游 coverage 计数缺失/为 0 | cov_n、sub_n 用 or 0；scope_ratio 先置 1.0，只有 sub_n>1 且 0<cov_n<sub_n 才缩放（deep_question.py:2549-2557） | None/0/invalid 均不缩放，等价 coverage=100%。deep_question 自身 submission builder 不生产这两个 coverage 字段（deep_question.py:6079-6123），所以该默认在此入口可达。 |
| B. coverage reconciler 返回 None | 题面解不出至少 2 问、无 points、或全部 point 无法归属时直接 return None（rubric_grader_v1.py:671-700） | _grade_one_case_v1 只在结果是 dict 时写 coverage/未覆盖声明（deep_question.py:2655-2666）；None 无 marker、无降级。 |
| C. 解析/对账异常被吞 | coverage 块 except Exception: pass（deep_question.py:2657-2668）；TutorBot 计数 helper 异常返回空 dict（tutorbot/agent/loop.py:91-100） | 异常与合法全覆盖在下游不可区分，仍继续出数字分。 |

终端还会放大这个问题：build_case_subq_coverage_note(None) 返回空串（rubric_grader_v1.py:710-720）；render 无 note 时按普通整题口径显示（rubric_grader_v1.py:831-845,986-995）；score-first stream 也只在有 note 时标“仅已覆盖小问”（rubric_grader_v1.py:1247-1259）。

### 4.2 三态判别逻辑

建议返回显式对象：

    coverage_state = single | known | unknown | error
    total_count
    covered_count
    covered_indexes
    uncovered_indexes
    authority_source
    reason

判别顺序：

1. 优先读上游明确 scope authority，不用“解析不出”推断单问。TutorBot 已能从实际采纳 matched_indexes 得分子（tutorbot/agent/loop.py:1584-1594,1619-1663），并把去重采纳数与题面标题数放进 ctx（tutorbot/agent/loop.py:1824-1857）；这应升级为通用 grading ctx 合同，而非 TutorBot 私有 hint。
2. 合法单小问 single：只有 source authority 明确它是原子小问时成立，例如唯一小问 qid/display_index 且 record 自带 nominal，或 canonical ctx 显式 subquestion_count=1。此时 covered=total=1，可正常数字判分。
3. 已知多问 known：total>=2 且 1<=covered<=total。covered<total 必须缩放并声明；covered==total 才是真全覆盖。
4. 矛盾 error：covered>total、已知多问但 covered=0、索引越界/冲突、上游声明 single 但题面确定解析出多问。
5. 证据不足 unknown：标题解析为 0/异常且无显式 subquestion_count=1，或所有 rubric points 无法归属。绝不能因 len(titles)<2 就视为单问。

fail-loud 行为：

- single/known 才能进入数字 finalizer。
- unknown/error 时，_grade_one_case_v1 返回现有 marker 形状，例如 {"status":"unavailable","reason":"coverage_unknown"}，或只给无数字的 diagnostic feedback；不得保留 scope_ratio=1.0。现有 marker 合同见 deep_question.py:2618-2626,2643-2653。
- 同时导出 score_authority="v1_unavailable:coverage_unknown:<reason>"。TutorBot 已有可复用的 V1 unavailable marker 形状（tutorbot/agent/loop.py:1959-1970）。
- render 不再把 unknown 转为空 note；若仍渲染，必须明示“无法确定判分范围，不输出数字成绩”。
- except Exception: pass 改为 coverage_state=error + authority marker；可以不让对话崩溃，但数字分不能 fail-open。

这样不会误伤合法单问：放行依据是显式原子问 authority，不是解析器没找到第二问。

### 5.2 修复实施顺序

1. 先收 coverage authority：所有入口统一产出 single/known/unknown/error；unknown/error fail-loud。否则 cap 没有可信 effective_scope_cap。
2. 锁定两个不同事实：nominal_full_score 与 effective_scope_cap，不再让 max_score 跨层表示两种意思。
3. 在 rubric_grader_v1 建唯一 finalizer：缩放后求和、封顶、有限数检查、一次写 event；同时统一普通/PGO rounding reconciliation。
4. 删除竞争 writer：删 deep_question.py:2684-2691 的事后改写；把 batch aggregate 迁到同一 grading authority，并保留 child authority/scope。
5. 修投影合同：render/stream/presentation/learning/observability/outcome 只读 final event，并对 unknown/error 显示无数字降级。
6. 正确性稳定后再上 final-result cache；先版本化 key/失效，再做共享存储与 single-flight，不能先把当前错分粘住。
7. 最后做分层验证。本次按禁令未运行测试；未来至少覆盖 tier-1 池超额、tier-2 2/4、coverage unknown、合法单问、tier-3 diagnostic、mixed batch、同题同答跨 worker、cache invalidation。

### 5.3 你没问但我必须说

#### A. 截断 rubric 的 partial salvage 会被重新归一到目标满分

_parse_extracted_points 在 JSON 截断时保留最后完整 object 以前的部分 points，并称“partial points better than none”（rubric_grader_v1.py:1920-1954）；下游却无条件把这个不完整池归一到 scope/full target（deep_question.py:2537-2557,2568-2577）。

这会把缺失点移出分母，再把幸存点拉满目标分值，系统性抬高命中幸存点的学生。salvaged_truncated 必须成为 fail-loud/degraded rubric，至少不能按完整 rubric target 发数字分。

#### B. batch merge 会洗掉子事件证据级别

aggregate 无论子事件来自 tier-1/2/3，都固定写 grading_source="rubric_scored_v1"、answer_key_authority="exam_reference_answer"、rubric_provenance="batch"（deep_question.py:2752-2765）；tier-3 单题原本是 derived_from_stem_pending_calibration、diagnostic/high-risk/non-official（deep_question.py:2695-2702）。

mixed batch 因而可把“官答分 + 题干推导诊断分”包装成统一官答 aggregate。这是证据级别伪装。batch 应要求 child authority 同质，或保留 per-item authority 并让 aggregate 继承最弱 child 的证据级别。

#### C. PGO rounding 与 partial_ratio=0 都有偏分风险

- PGO 每点用 round(display_max×credit,2)，题级却用 official_total×coverage（rubric_grader_v1.py:239-284）。总分不可整除或有 partial 时，逐点和可与总分不同；应由 finalizer 做 drift repair。
- PGO 使用 ratio=float(verdict.get("partial_ratio") or default)（rubric_grader_v1.py:245-250）。若 judge 明确返回 status=partial、partial_ratio=0，falsy 语义会将 0 改成 0.5，直接向系统有利地加分。必须用“键缺失/is None”判断默认值。

#### D. observe-only marker 在 TutorBot 可达链上不完整

authority 白名单列有 point_pool_exceeds_max、case_subq_coverage、case_subq_uncovered（case_output_policy.py:38-69），但 TutorBot 从 event 提升到 runtime metadata 的显式 tuple 只列 adjudication count、score mismatch、bank slot、stem fallback、partial scope，缺这三键（tutorbot/agent/loop.py:1976-1987）。

所以“event 内写了 marker”不等于“生产 sink 可观测”。本次未查生产 trace，只能确认源码提升 tuple 缺键，不能声称所有外部 sink 实际都缺数据。

#### E. 非有限 score 没有硬拒绝

_parse_extracted_points 只检查 score<=0（rubric_grader_v1.py:1955-1973），没有 math.isfinite；compiled score 也直接 float 并累加（rubric_grader_v1.py:149-166）。唯一 finalizer 必须先拒绝 NaN/Infinity/负数，再求和和封顶。

### 5.4 证据边界与收口

- claim level：当前工作树源码的静态结构判断，不是“已修好/已上线”。
- evidence level：逐行源码与调用点静态交叉；未执行测试、模型调用、trace 或生产直查。
- 分母：已穷举两个核心对象中 awarded_score/max_score、tier、batch、coverage、render/stream、outcome 的相关位置，并补查 TutorBot 直接调用与 coverage 上游。
- 未覆盖：动态猴补、仓外消费者、生产 flag 实时值、真实 bank 数据分布、多 worker cache、实际 LLM 方差、持久化终态。
- 最小下一步：先做 coverage 三态 + 唯一 finalizer 输入合同与反例测试，不要先加 result cache。

真正坏掉的一等业务事实是：“这次作答，在这道题真实满分与实际判分范围下，学生唯一应得多少分。”

争夺该事实 authority 的位置包括：rubric 点池和、construction_grading_result.max_score、coverage scope、grade_with_rubric 事件组装、_grade_one_case_v1 事后分母还原、batch wrapper 求和，以及 render/outcome 对上游事件的盲信。

推荐方案更接近 single authority，因为它不在 render、outcome 或 wrapper 再加校正，而是先将 nominal/scope 收成明确输入，再让 rubric_grader_v1 的唯一 finalizer 一次写分，其他层全部降为只读投影。

“你没问但我必须说”三项 Stop Gate：

1. 前提质疑：“封顶只加一个 min”不成立；未先统一 scope 坐标与 writer，min 只是新 patch anchor。
2. 层盲区：本次落在 grading kernel + capability projection；未动态验证同一 event 写入 Learning Brain 后的 scope 保真，也未验证仓外 terminal/frontend 是否再解释分数。
3. 坏消息：当前源码中封顶仍 observe-only、coverage unknown 仍 fail-open、final-result cache 不存在，且部分 marker 的 TutorBot 提升链缺键。本报告只完成静态定位与收敛设计，**没有修复、没有测试、没有部署**。
