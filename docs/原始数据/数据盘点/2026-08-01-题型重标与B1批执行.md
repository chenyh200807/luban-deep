### 1.3 抽样发现的争议 → 全量量化 → 划批

抽样暴露的问题不是"分类错了"，而是"后两个来源的**答案本身已经没了**"。对 1547 行做全量答案形态实测：

### 2.4 为什么选 `essay`

17 个枚举值里，不含 `case`、且非客观题（不触发 `qb_is_valid_objective_row`）的只有：
`calculation` 族、`fill_in_blank`、`diagram_interpretation`、`recall`、`essay`。

- `fill_in_blank` 语义上更贴那 267 行带 `______` 的填空题，但它**不在任何判分分道集合里** →
  `grading_packet_builder.select_lane()` 会落到 `LANE_RETRIEVAL`（不出判分结论）。对一道有标准答案的填空题，这是回归。
- `recall` / `diagram_interpretation` / `calculation` 同理，且语义更不准。
- `essay` 是唯一一个**已被现有词表认识**、且落在主观题判分道上的值。

→ 全部 627 行统一写 `essay`。代价是 267 行填空题被叫成"简答题"——不精确，但两者都是"对参考答案判的开放题"，
且严格优于现状的 `case_study`。**单一值优于两个值**：两个值会让消费面推理面翻倍，收益却是负的。

```sql
where id = any($B1$::bigint[]) and deleted_at is null order by id;

-- 步骤 2：软删（分批 ≤100，每批回读断言）
update public.questions_bank set deleted_at = now()
where id = any($B1_CHUNK$::bigint[])
  and deleted_at is null
  and original_id ~ '^EXAM_(19|20)[0-9]{2}_'   -- 护栏：血统限定
  and source_chunk_id is null                   -- 护栏：正主一定有 chunk，误入的会被挡
returning id, deleted_at;

-- 回滚
update public.questions_bank set deleted_at = null where id = any($B1$::bigint[]);
```

**但收权必须先于软删落地**，否则软删只是加了一列没人读的字段：
读取面（`supabase.py` 的 exact/ilike 探针、两个 RPC `search_questions_bank_vector` / `search_questions_bank_text`、
`blueprint_service._rest_get`）**全部**要加 `deleted_at is null`。
现状是**全表可达、无 active-set 闸门**（07-30 计划 §4 已实证）。
**在读取面收权之前执行软删 = 数据没删掉、行为没变化、只多了一列 —— 属于自欺。**

## 5. 缺口与诚实边界（你没问但必须知道的）

1. **`essay` 这个新值只是"不那么错"，不是"对"。** 267 行带 `______` 的填空题被叫作简答题。
   之所以不用更准的 `fill_in_blank`，是因为它不在任何判分分道集合里、会把这些行推进 `LANE_RETRIEVAL`（不出判分结论）。
   **准确性让位于分道正确性，这是一个有意识的交换，不是疏忽。** 真正的解是把词表补齐（代码改动，另立项）。
2. **920 行跳过批是"登记"，不是"完成"。** 它们今天仍然是 `case_study`，仍然会被 RAG 案例分支收走。
   本次只治了 1547 里的 40%。剩下 60% 的**前置条件是 B8/B11 把答案补回来**——
   在答案回源之前重标，只是把一个错标签换成另一个错标签。
3. **本次没有做任何内容正确性的教材溯源核验。** 627 行的答案"是散文、非规则转储、长度合理"是**形态**判断，
   不等于"答案正确"。§1.2 抽的 10 行里，`17634` 的答案是 `脚手架定期检查的主要内容：`——**截断了**。
   这属于既有数据缺陷（A6 证明本次写操作未造成任何非 `question_type` 字段漂移），但说明这批数据**不是干净的**，
   只是"答案字段有内容"。真实答案质量需要单独一轮回源核验。
4. **`check_qb_question_type_enum` 不在仓库里，这本身是个治理缺口。** 线上 DB 有一条 17 值的硬白名单，
   而 `supabase/migrations/` 里既没有它、也没有 `questions_bank` 的建表 DDL。
   任何人在代码里新增一个 `question_type` 字面量、然后试图写库，都会在运行时被 DB 400 拒——
   而本地测试和 CI 都发现不了（测试里的 `weird_new_type` / `x` / `qa` 从不落库）。
   **建议把线上 DDL 反向导出成 migration 补进仓库**，否则"仓库是权威"这句话对这张表不成立。
5. **B1 的 319 行是在"今天的快照"上重建的。** 与 07-30 逐数吻合是强佐证，但两次之间若有人写过库，
   吻合也可能是巧合。执行前必须按 §4.5 步骤 1 重新只读复核，不得直接用 `b1_ids.json`。
6. **软删列缺失是 B1 的唯一阻断项，但不是唯一风险。** 即使加了 `deleted_at`，
   §4.5 末尾那条"读取面收权必须先于软删落地"如果不做，整个软删方案是自欺。
   收权涉及 5 个读取通道（含 2 个 DB 侧 RPC，改 RPC 是 DDL），**工作量远大于加一列**。
7. **本次 PATCH 没有触发任何 CHECK 拒绝**，但这是因为 `essay` 恰在白名单内且非客观题类型。
   若将来有人要引入白名单外的新题型，**必须先改 DB 约束，且改约束前要确认存量行不违反新约束**——
   `check_qb_core_sources_objective_quality` 会对 `REAL_EXAM` / `TEXTBOOK_ASSESSMENT` 全表复验。
