微信小程序意见反馈 · 学情模块同款视觉

把“意见反馈”从一个输入框升级成产品质量闭环

当前“我的 → 意见反馈”只有一个文本弹窗，用户难以说明问题，团队也难以定位根因。 新方案保留轻量入口，同时补齐问题类型、图片/视频附件、自动上下文、追问引导、后台分诊和质量回流。

20 秒普通用户完成一次有效反馈
3 步选择问题 → 补证据 → 提交
1 个 intake用户侧统一入口，后台保留来源
0 重复真相不让前端或 BI 变成反馈 authority

执行边界

本页是评审方案，不是生产实现。它应挂在现有“鲁班智考反馈 Top10 修复 / BI 反馈中心”主线下。

Design Proposal

Assumptions

首要场景是微信小程序“我的”页反馈；其次覆盖聊天消息点踩、学情/测评/支付等上下文反馈。

Simplest Path

先做一个全屏反馈页和附件能力，不重做客服系统、不新建聊天入口、不把所有反馈混成一张无来源大表。

Change Boundary

触碰用户反馈入口、反馈提交 payload、附件 sidecar、BI 反馈中心读模型；不改 TutorBot 主链路。

Verification Target

WeChat DevTools 可上传图片并提交；Supabase/后台可看到结构化字段、附件、页面上下文和处理状态。

外部调研结论

顶尖产品不是让用户写作文，而是让用户用最少动作给出可定位证据。

Research-backed
Apple Feedback Assistant诊断 + 附件

强调尽早提交、一个报告只讲一个问题、标题要包含平台/版本/关键信息；UI 问题应附截图或录屏，并自动收集诊断信息。

可借鉴：自动带上页面、版本、网络、trace；引导“实际结果 / 期望结果 / 复现步骤”，但只在需要时展开。

Discord Bug Report结构化表单

把问题拆成描述、复现步骤、期望结果、实际结果、客户端信息、debug logs、附件。

可借鉴：对“系统出错”类反馈启用结构化追问；对普通建议保持轻量。

Slack Troubleshooting自动日志

用户只写简短摘要，日志在提交时自动附上，降低用户负担，同时提高工程定位效率。

可借鉴：小程序提交时自动附 recent route、last request ids、网络状态、客户端版本，而不是要求用户手动说明。

Luciq / Instabug选择题优先

建议用互斥选项、具体问题、先问最重要的问题，并允许 Other / 不确定，避免笼统开放题。

可借鉴：第一屏先让用户选问题类型和症状标签，文本说明变成可选增强，不作为唯一入口。

FeedAIde 研究上下文追问

上下文感知追问能让反馈更完整；研究中用户认为它比简单表单更容易、更有帮助。

可借鉴：P2 增加“智能补问”：只在反馈信息不足时问 1 个问题，不让 AI 接管分诊 authority。

微信小程序能力图片 / 视频

微信生态可用 chooseMedia 选图片/视频，再上传到云存储；审核版本需要声明 chooseMedia 隐私权限。

可借鉴：支持最多 3 张图或 1 段短视频，默认压缩，明确隐私提示和删除按钮。

现状诊断

仓库现状说明：消息点踩已有标签，Profile 反馈仍是一个 modal 输入框，后台已有 ai_feedback 与 BI 反馈中心基础。

Current Gap

现在的问题

  • “我的 → 意见反馈”打开的是 `wx.showModal editable`，只能写一段文本。
  • 不能选择问题类型：登录、支付、AI 答案、题目答案、页面显示、加载慢等被混成“产品反馈”。
  • 不能上传照片或录屏，UI 问题需要用户自行描述，丢失最关键证据。
  • Profile 反馈没有页面上下文、设备、网络、最近接口、trace 的明确采集协议。
  • 聊天消息点踩和全局反馈是两套体验：前者有标签，后者没有；后台聚合会有噪声。

真正坏掉的一等业务事实

不是“缺一个好看的表单”，而是“用户遇到的问题事实没有被完整、结构化、可追踪地写入反馈系统”。 这会导致运营看到情绪，工程看不到上下文，教研看不到题目证据，产品看不到优先级。

缺证据 缺分类 缺上下文 缺闭环

推荐方案：轻入口，重证据，后台闭环

用户侧只看到简单流程；系统侧自动收集足够定位问题的上下文。

用户侧原则

  • 默认 3 步完成：类型、症状、提交。
  • 文本可选，但“建议”和“题目错误”场景会鼓励补充。
  • 图片/视频入口显眼，支持删除和预览。
  • 提交后给反馈编号和进度，不只说“感谢”。

团队侧原则

  • 每条反馈带 source、surface、route、problem_type、symptom_tags。
  • 附件与日志是 evidence，不进入文本 comment 混存。
  • BI 反馈中心按 owner 分流：产品、工程、教研、运营。
  • 处理结果写 audit，可回看、可复盘、可统计 SLA。

关键取舍

不建议把反馈入口做成“在线客服聊天”。第一阶段用户需要的是低摩擦提交，团队需要的是证据完整。 客服对话可以作为后续处理通道，但不应该替代结构化 intake。

信息架构

反馈不是单表单，而是一条从用户问题到产品修复的链路。

入口

我的页、聊天点踩、错误态按钮、学情/测评页面的“报告问题”。

分类

系统问题、答案问题、题目/教研问题、体验建议、支付会员。

证据

截图、录屏、页面 route、trace/request id、设备网络、关联题目/消息。

分诊

自动 owner 建议 + 人工确认；去重、优先级、SLA、状态。

闭环

用户进度、BI 统计、Top10 问题域、修复证据、回归验证。

字段与单一 authority

避免“前端一套、BI 一套、运营备注一套”的反馈真相漂移。

Authority Design
业务事实 唯一写入/读取建议 必须字段 不要做
用户提交了一条问题反馈 `FeedbackIntakeService` 统一归一化；消息反馈继续兼容现有 `ai_feedback`，全局问题走反馈 report authority。 feedback_id、user_id、source、surface、route、problem_type、symptom_tags、comment、created_at。 不要让 profile modal 直接拼接无结构 comment；不要让 BI 前端写业务真相。
用户提供了可定位证据 `feedback_attachments` sidecar；文件存储只保存 file id / hash / mime / size / width / height。 attachment_id、feedback_id、kind、storage_key、thumb_url、redaction_status、upload_status。 不要把图片 base64 塞进反馈表；不要公开永久 URL。
系统自动采集上下文 `feedback_context_snapshot` 随 intake 写入，只保存必要调试字段。 app_version、route、network_type、device_model、last_request_ids、trace_id、session_id、message_id。 不要采集通讯录、相册列表、隐私文本；不要把日志采集做成默认全量录屏。
团队处理了反馈 BI 反馈中心写 `feedback_triage` audit；状态变更必须有 owner、reason、idempotency key。 status、priority、owner_team、resolution、linked_issue、handled_by、handled_at。 不要用本地状态覆盖后端状态；不要忽略冲突写入。

问题类型设计

让用户容易选，也让后台可以分派到真正的 owner。

工程

系统出错

打不开、卡住、加载慢、按钮无响应、登录异常、上传失败、页面显示错乱。

教研 + 模型

答案 / 题目有问题

事实错误、解析看不懂、标准答案不一致、题目选项错误、没有引用依据。

产品

体验建议

不好找、流程麻烦、希望增加功能、视觉看不清、操作路径不符合预期。

运营

支付 / 会员

充值失败、权益未到账、余额异常、套餐说明不清、发票/订单问题。

学情

学习记录问题

错题没记录、报告不准、训练推荐不对、历史对话找不到、进度异常。

兜底

其他 / 不确定

允许用户不知道问题属于哪里，但后台必须再分诊，不让“其他”成为垃圾桶。

落地阶段

先让用户能提交高质量证据，再做智能追问和跨模块质量闭环。

P0 / 2-3 天

替换 Profile 单输入框为全屏反馈页

  • 新增问题类型、症状 chips、可选描述、最多 3 张图片或 1 段短视频。
  • 自动上下文 snapshot：route、app version、network、last request ids、user anonymous id。
  • 提交成功返回 feedback_id；失败保留草稿并支持重试。
  • WeChat DevTools 验证 chooseMedia 隐私配置、上传、删除、弱网失败态。
P1 / 4-6 天

统一消息点踩与全局反馈的字段协议

  • 聊天点踩继续轻量，但补齐 problem_type 和 context_snapshot。
  • BI 反馈中心展示附件、页面、owner、状态、SLA 和处理记录。
  • Top10 issue register 从反馈中心生成候选问题域，人工确认后进入修复队列。
P2 / 1-2 周

智能补问与去重聚类

  • 仅当缺少关键字段时补问一个问题，例如“这个问题能稳定复现吗？”
  • 用上下文和截图摘要做相似反馈聚类，降低重复 triage 成本。
  • 向用户显示“已有类似问题，已合并跟进”，但保留个人反馈编号。

验收清单

这个模块上线前不能只看页面能点，要证明“证据被正确写入并可处理”。

用户体验 Gate

  • 不写长文本也能提交一个可分诊反馈。
  • 照片/录屏可添加、预览、删除、失败重试。
  • 弱网/上传失败不丢草稿。
  • 提交后能看到反馈编号和处理状态入口。
  • 页面文案不要求用户懂“trace / request id / authority”。

后台闭环 Gate

  • Supabase/存储能查到结构化字段、附件 sidecar、上下文 snapshot。
  • BI 反馈中心能按 problem_type、owner、status、source 过滤。
  • 反馈状态变更写 audit，重复提交可幂等处理。
  • 敏感信息脱敏：手机号、token、完整日志、相册路径不得裸露。
  • 能从一条反馈跳回相关页面、消息、题目或订单证据。

参考来源

本方案参考了移动端反馈、bug report、in-app survey 与小程序上传能力资料。

  1. Apple Feedback Assistant：诊断信息、一个问题一份报告、截图/录屏、状态与相似报告。
  2. Discord: How to Report a Bug：描述、复现、期望/实际结果、日志与附件。
  3. Slack Troubleshooting：报告问题时自动附加日志。
  4. Luciq / Instabug In-app Surveys：选择题优先、具体问题、允许 Other。
  5. Material Design Text Fields：输入字段应清晰、可发现、便于纠错。
  6. FeedAIde：上下文感知追问提升反馈完整度。
  7. CloudBase 微信小程序文件上传：chooseMedia、上传、隐私权限配置。
