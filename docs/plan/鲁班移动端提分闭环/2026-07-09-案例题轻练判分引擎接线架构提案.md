## 1. 现状(只读核实)

生产案例判分主链(V1 Nexus,`data-authority.md` / 接线地图):
```
deep_question._grade_one_case_v1(qid, 学员作答)
  → rubric_grader_v1.load_rubric(qid)      # 编译库采分点 {point_id,text,score,policy,required_terms}
  → grade_with_batch_judge_async(...)       # 逐点 LLM 裁决(DeepSeek batch_judge)
  → _pgo_credit(policy, status, ratio)      # 按 policy 折算 hit/partial/miss → 分
```
**关键问题**:`policy ∈ {exact_required, qualitative, calc, list, boolean_judgment}` **全部走同一个 LLM judge**。即**计算类(calc)、组合类(set)、排序类现在也靠 LLM 判**——这正是 §1 决断"计算类判分绝不走 LLM"要治的,也是本轮 7 个确定性引擎要替下来的。

## 2. 提案:在 LLM judge 前加一道**确定性 policy 分发**(ADD,不删现有)

在 `load_rubric` 之后、`batch_judge` 之前,按 policy/question_type 把**确定性可判**的题分流到新引擎;**LLM judge 只保留 `qualitative`(语义判读)**:

| policy / 题型 | 路由到(本轮已建引擎) | dispatch kind |
|---|---|---|
| `calc`(造价/挣值链) | DAG+ECF `grade_calc_dag` | CALC_DAG |
| 荷载组合(矩阵) | 集合精确匹配 `grade_set_membership` | SET_MEMBERSHIP |
| 工序排序 | 拓扑序 `grade_ordering` | ORDERING |
| 判断改正 | 合取门 `judge_flaw_correction` | CONJUNCTION |
| 关键线路 | CPM `matches_critical_path` | CPM_CRITICAL_PATH |
| `qualitative` / `exact_required` | **保留现有 LLM batch_judge** | —(不动) |

分发通过已建的 `case_grading_dispatch.dispatch_grade(kind, spec, student)`。**采分点来自 `case_scoring_point_resolver.resolve_scoring_points(qid)`**(白名单门 + 质量闸 + 教研 review 的 sub_no + 编译库原文),未过教研验收的 qid 走不到确定性分发(fail-closed)。
