## 1. 本次计划的结论

本计划把 `/bi` 从“经营看板”升级为“会员经营后台 + BI 决策系统”。它不是一次视觉换皮，也不是把所有功能堆到一个大屏里，而是把经营判断、会员管理、套餐权益、充值账务、会员对话、反馈处理、质量成本和审计留痕收成一条可执行链路。

一句话定义：

> 让团队从同一个后台完成“发现经营问题 -> 定位会员 -> 查看证据 -> 执行动作 -> 记录结果 -> 回看效果”。

推荐路线：

1. 保留现有后端 authority，不新造平行会员、钱包、反馈或聊天真相。
2. 前端重做信息架构、布局、设计系统、表格、抽屉、筛选、队列和可视化。
3. P0 先交付后台 shell、经营总览静态原型、会员经营闭环、全局手机号搜索、账务只读、对话摘要审计、AI 消息反馈和关键动作审计。
4. P1 再交付套餐编辑、复杂对账、全量反馈处理流转、团队保存视图、高级批量运营、暗色模式和更复杂的运维面板。

## 2. Karpathy Gate

### 2.1 assumptions

本计划采用以下需求解释：

- 用户要的不是“BI 页面更漂亮”，而是一个能支撑运营、增长、成本、会员管理和反馈闭环的专业后台。
- 现有功能都要保留：老板工作台、会员运营、学员 360、上线面板、内测申请、经营审计、BI 指标、成本质量等。
- 新需求明确增加：套餐管理、会员对话管理、充值记录、会员反馈多模块聚合、账务与运营动作闭环。
- 当前阶段优先在现有数据和服务上做可交付升级，不能为了“顶尖”先引入重型数仓、复杂 CRM 工作流或第二套支付中台。

不确定项：

- 套餐 catalog、订单、支付渠道、退款和充值流水是否已有稳定 canonical 表。
- 多个反馈模块的真实存储位置和字段是否已经统一。
- 会员对话全文的隐私、审计、脱敏和访问权限是否已有生产级策略。
- 5 万会员下，高维筛选、全局手机号搜索和会员详情抽屉的 SQL / API 性能是否能稳定进入预算。

这些不确定项不能阻塞 UI/UX 主计划，但必须在 Batch 0 做 authority audit。

### 2.2 simplest path

最短可交付路径：

1. 不重写后端主业务能力。
2. 不新增 BI WebSocket。
3. 不新增聊天入口。
4. 不新增前端本地事实源。
5. 先用现有 `BIService`、`MemberConsoleService`、wallet service、session store、feedback / invite-test / observability API 组装统一后台。
6. 前端先落新的 shell、导航、数据密度、表格、详情抽屉、风险队列、总览原型和只读中心。
7. 每个 Batch 都必须由 feature flag 包住，并预先写好 1 秒回滚 runbook；没有回滚演练，不算上线。

这条路径比“一次性做完整 CRM + 商品系统 + 支付对账 + 数仓”更稳，因为它先把团队每天会用的运营闭环交付出来。

### 2.3 change boundary

本计划允许后续实现触碰：

- `web/app/(workspace)/bi/**`
- `web/app/(workspace)/member/**`
- `web/lib/bi-api.ts`
- `web/lib/member-api.ts`
- `deeptutor/services/bi_service.py`
- `deeptutor/services/bi_metrics.py`
- `deeptutor/services/member_console/service.py`
- `deeptutor/api/routers/bi.py`
- `deeptutor/api/routers/member.py`
- 相关 tests 和 docs

本计划不允许后续实现顺手触碰：

- `/api/v1/ws` 聊天 transport
- TutorBot runtime 身份体系
- learner state canonical write path
- wallet ledger canonical write path
- 生产支付渠道配置
- 微信小程序主入口 UI

如果必须触碰上述边界，必须单独开计划或追加 contract 审查。

### 2.4 verification target

完成标准不是“页面看起来高级”，而是：

- 老板 3 秒内能判断经营健康和最大风险。
- 运营 1 次点击能从风险项进入对应会员队列。
- 运营在同一入口能完成会员筛选、查看证据、执行动作、留痕。
- 套餐、充值、钱包、权益变更不产生第二套账务真相。
- 会员对话默认摘要优先，全文查看必须审计。
- 多反馈模块可统一查看，但不合并成混乱单表。
- 成本能下钻到会员、会话、能力或模型维度，但不把估算值伪装成 A 级事实。
- 每个跨页面 KPI 都 import 同一个 `metric_id` 定义，不允许不同页面 hardcode 同名指标。
- 危险动作默认有 5 分钟撤销窗口；撤销也必须写正向和逆向 audit。
- Playwright 覆盖桌面 `1440x900`、iPad 横屏 `1024x768` 和移动 `375x812`，无横向滚动、无文字溢出、无主要按钮不可达。

## 3. 一等业务事实与单一 authority

### 3.1 one business fact

本系统要维护的一等业务事实是：

> 每个会员当前值不值得运营、为什么、该做什么、做了以后有没有结果。

这个事实由多个子事实组成，但它们不能互相抢权。

### 3.2 authority map

| 子事实 | 唯一 authority | BI / 前端职责 |
| --- | --- | --- |
| 会员身份、手机号、状态、tier、到期时间 | `MemberConsoleService` / auth identity | 读取、筛选、展示、发起后台动作 |
| 钱包余额、点数、充值入账、扣点 | wallet ledger / Supabase wallet authority | 读取余额和流水，触发受控补偿动作，不本地算余额 |
| 套餐定义、权益包、上下架状态 | 待 audit 的 package catalog authority | P0 只读或配置草稿，未确认前不做生产编辑 |
| 订单、充值、退款 | 待 audit 的 payment / order authority | P0 只读对账，异常入队，不重写支付链 |
| 会员对话记录 | session store / chat message store | 摘要优先展示，全文按需加载并审计 |
| 学习事实、错题、掌握度、训练建议 | learner state / learning evidence read model | 作为学员 360 证据面，不在 BI 写学习事实 |
| 会员反馈 | 各反馈来源的 canonical table / service | 统一聚合和流转，不把所有反馈塞入一个新真相 |
| AI 质量、失败回合、成本 | observability / Langfuse / BIService | 汇总、下钻、标可信等级 |
| 后台操作记录 | member audit log | 所有敏感动作必须写审计 |

### 3.3 competing authorities to avoid

禁止出现以下重复真相：

- 前端 local state 维护“会员状态”并参与业务判断。
- BI API 写会员状态或写学习状态。
- 套餐编辑直接覆盖历史订单套餐快照。
- 充值记录和钱包流水用同一个列表混展示，导致金额、点数、权益含义混乱。
- 会员反馈、AI 消息反馈、内测反馈、运营备注混成一个无来源字段。
- 对话全文默认暴露给所有后台用户。
- 成本估算和真实账单对账结果用同一可信等级展示。

### 3.4 canonical path

后台主链路：

```text
BI / member read model
  -> 风险队列 / 会员列表 / 套餐账务 / 对话回顾 / 反馈中心
  -> 会员详情抽屉
  -> 受控后台动作
  -> authority service write
  -> audit log
  -> BI refresh / action outcome
```

任何后续实现只允许把 UI 状态作为临时展示状态，不允许让 UI 状态成为业务事实。

### 3.5 admin write safety

所有后台写操作必须先满足三条硬约束，否则只能保留只读入口：

1. `idempotency_key`：所有 admin write 请求必须带幂等键，24 小时内同 key 返回首次结果，避免超时重试导致多扣、多补或重复撤销。
2. `etag` / `version`：会员详情、钱包摘要、套餐草稿和反馈处理对象必须返回版本；写入时携带版本，冲突返回 412，并在前端明确提示“该对象已被另一操作修改”。
3. `undo_window`：撤销会员、补点数、异常处理、反馈状态批量变更等危险动作默认 5 分钟内可撤销；audit 同时记录原动作、撤销动作、操作者、原因和关联对象。

P0 只开放低风险写操作：标记已联系、添加备注、加入跟进队列、AI 消息反馈 triage。开通/撤销/补点数/异常处理必须等上述三条在后端和前端都验收后再开放。

### 3.6 metric authority

经营总览、会员运营、商品账务、反馈中心和系统运维里的同名指标必须共享同一个 `metric_id` 和口径说明：

- KPI 卡片、趋势图、表格列、导出字段都从同一指标定义导入。
- 每个 KPI hover / tooltip 必须展示口径、时间窗口、authority、可信等级、更新时间和 owner。
- C/D 级可信指标只能提示趋势或风险，不能作为财务结算或自动动作依据。

## 4. 用户角色与核心场景

### 4.1 老板 / 创始人

每天打开一次，回答：

- 今天业务健康吗？
- 增长、付费、留存、续费、成本哪个最危险？
- 会员经营今天最该处理哪 3 件事？
- AI 教学质量有没有影响付费和续费？
- 成本有没有失控，是否高成本低效果？

必须支持：

- 一屏看北极星、收入、成本、风险和行动队列。
- 点击风险项进入对应会员或账务下钻。
- 查看数据可信等级，不被假精确数字误导。

### 4.2 运营 / 班主任

每天处理会员队列，回答：

- 哪些会员即将到期？
- 哪些付费会员沉默？
- 哪些会员聊了很多但没形成学习成果？
- 哪些会员差评、投诉或反馈最多？
- 哪些会员需要补偿、续期、提醒或人工跟进？

必须支持：

- 高密表格筛选。
- 保存运营视图。
- 批量动作。
- 学员 360。
- 备注和跟进结果。
- 对话和反馈证据。

### 4.3 增长 / 销售

关注：

- 从注册到付费的漏斗掉点。
- 内测申请和真实会员转化。
- 渠道、来源、活动、套餐之间的差异。
- 充值和续费趋势。

必须支持：

- 增长漏斗。
- 渠道 / 来源维度。
- 套餐转化。
- 付费前对话和反馈样本。

### 4.4 教研

关注：

- 学员是否真正学会。
- 哪些章节薄弱。
- 哪类题目、解析或 AI 回答引发差评。
- 反馈是否能回到题库、解析和教学策略。

必须支持：

- 学习效果摘要。
- 反馈按知识点 / 题型 / 章节聚合。
- 从反馈跳到对话和作答证据。

### 4.5 工程 / 产品

关注：

- 失败回合。
- 慢请求。
- RAG / 工具 / 模型质量。
- 成本异常。
- 数据降级。
- 权限和审计。

必须支持：

- 成本质量中心。
- 数据可信中心。
- release / launch readiness 下钻。

### 4.6 客服 / 用户支持

接到投诉电话或微信消息时，1 分钟内回答：

- 这个人是谁，是否付费，当前套餐和权益是什么？
- 最近一次充值、退款、补偿、扣点是否正常？
- 最近对话、差评、投诉、运营备注发生了什么？
- 应该转运营、教研、工程还是财务处理？

必须支持：

- 顶部全局搜索手机号、微信昵称、user_id、订单号。
- 搜索结果直接打开学员 360。
- 会员详情里同时看到订单、钱包、对话、反馈和运营备注。
- 轻动作：标记已联系、加备注、加入跟进队列。

### 4.7 财务对账

每周或每月对账时，回答：

- 自然月收入、退款、补偿和点数变化是否能对上。
- 不同支付渠道、套餐、发票状态的差异在哪里。
- 哪些订单已支付未入账、重复入账或退款未扣权益。

必须支持：

- 按自然月聚合。
- 按支付渠道分组。
- 按发票状态筛选。
- 订单和钱包流水并列查看，但不混成同一事实。

### 4.8 会议与大屏模式

晨会、周会、投影场景需要一个只读的 `/bi/standup` 路由：

- 只展示 KPI、今日行动队列、核心趋势和异常提醒。
- 不展示会员隐私详情。
- 不提供写操作。
- 适配会议室宽屏和 iPad 横屏。

## 5. 信息架构

一级导航采用 5 个主区，而不是 8 个散 tab。v1.1 采纳“对话按会员看、反馈按问题看、系统风险单独看”的结构：

1. `经营总览`
2. `会员运营`
3. `商品账务`
4. `反馈中心`
5. `系统运维`

理由：

- 老板视角不应被内部模块切碎。
- 运营工作流必须从会员对象出发。
- 套餐、充值、订单、钱包天然是一组；账务异常是行动队列，不是普通 tab。
- 对话回顾天然按会员发生，应并入会员运营和学员 360，而不是和反馈中心绑死。
- 反馈中心按问题分类和 owner 处理，避免运营、教研、工程在同一噪声池里疲劳。
- 成本、数据可信、操作审计、权限和上线面板属于系统运维面，不应混在老板经营页面里。

兼容路由：

- `/bi` 默认打开 `经营总览`
- `/bi?tab=member-ops` 映射到 `会员运营`
- `/bi?tab=commerce` 映射到 `商品账务`
- `/bi?tab=feedback` 映射到 `反馈中心`
- `/bi?tab=ops` 映射到 `系统运维`
- `/bi?tab=conversation-feedback` 兼容映射到 `会员运营`，并打开对话回顾视图
- `/bi?tab=quality-audit` 兼容映射到 `系统运维`
- `/member` 保留兼容入口，跳转或复用 `会员运营`
- `/bi/standup` 提供只读会议模式

## 6. 各主区设计

### 6.1 经营总览

目标：3 秒判断业务是否健康。

第一屏固定内容：

1. 顶部控制条：时间窗口、刷新、导出、全局筛选、全局手机号搜索、数据更新时间。
2. 北极星指标：有效学习成功会员数。
3. 经营 KPI 条：
   - 新增真实会员
   - 激活会员
   - 付费会员
   - 续费风险会员
   - 今日充值 / 收入
   - 今日 AI 成本
   - 单有效学习成本
   - 数据可信度
   - 每个 KPI 必须显示当前值、同比 / 环比或 WoW / MoM、可信等级和趋势方向。
   - 每个 KPI hover 必须展示 `metric_id`、口径定义、authority、owner、更新时间和降级说明。
4. 主趋势图：
   - 收入
   - 有效学习成功会员
   - 活跃会员
   - AI 成本
5. 今日行动队列：
   - 即将到期高价值会员
   - 高成本低效果会员
   - 付费后未学习会员
   - 差评或投诉会员
   - 账务异常

行动队列排序规则：

- 默认按“预期损失金额 / 续费风险 / 影响会员数 / 可信等级 / 更新时间”综合排序。
- 用户可切换为按收入风险、投诉风险、成本风险、账务风险排序。
- 已处理项当天不重复置顶，除非风险等级上升。

不展示：

- TutorBot 排行细节。
- 工具调用细目。
- 长篇介绍文案。
- 不能下钻的装饰指标。

### 6.2 会员运营

目标：成为真正可操作的 CRM 工作区。

布局：

- 左侧：保存视图和高级筛选。
- 中间：高密会员表格。
- 右侧：学员 360 抽屉或固定详情栏。

会员表格默认只展示 7 列，保证 `1440x900` 不拥挤：

- 选择框
- 会员姓名 / 昵称
- 手机号
- 套餐
- 状态
- 到期时间
- 最近活跃
- 风险等级

可选列通过列设置打开：

- user_id
- tier
- 最近充值
- 点数余额
- 当前焦点
- 最近反馈
- 建议动作
- 来源
- 跟进 owner
- 上次联系时间

常用筛选固定在表格上方，默认只保留 5 个：

- 搜索：姓名、手机号、user_id、微信、订单号。
- 状态：试用、正常、即将到期、已过期、已撤销、冻结。
- 套餐：体验包、VIP、SVIP、点数包、人工赠送。
- 风险：沉默、即将到期、高成本低效果、差评、投诉、低学习成果。
- 是否有未处理反馈。

高级筛选收进折叠面板：

- 来源：小程序、Web、内测、活动、人工导入。
- 最近活跃区间。
- 到期区间。
- 充值区间。
- 是否有未读对话风险。
- 是否有账务异常。
- 支付渠道。
- 发票状态。
- merge candidate。

动作：

- 开通会员。
- 续期会员。
- 撤销会员。
- 冻结 / 恢复。
- 补点数。
- 标记已联系。
- 添加备注。
- 记录跟进结果。
- 加入稍后联系。
- 导出当前筛选。

批量动作 P0 只允许低风险动作：

- 标记已联系。
- 加运营标签。
- 加入跟进队列。
- 导出。

批量动作交互规则：

- 勾选后必须显示“已选择 N 个会员”和当前筛选总数。
- N 大于 100 时禁用导出以外的写操作，提示缩小筛选范围。
- 低风险批量动作必须有 loading、success、partial failure 和 retry。
- P0 保存视图仅支持个人私有视图；P1 再做团队共享、权限和默认视图。

批量开通、撤销、补点数必须 P1 加二次确认、幂等、并发版本、5 分钟 Undo 和审计后再开放。

#### 6.2.1 对话回顾

对话回顾归入会员运营，而不是一级导航：

- 学员 360 内默认展示最近对话摘要、风险标签、成本、反馈状态。
- 对话列表拆成 `待处理` 和 `全部` 两个视图。
- `待处理` 只放差评、失败、需教研复核、高成本低效果、投诉相关对话。
- 全文默认折叠，查看全文必须选择原因并写 audit。
- 从风险队列连续打开多个会员时，抽屉提供 breadcrumb / 返回上一个会员。

### 6.3 学员 360

学员 360 是会员运营的详情层，不是独立大屏。

默认展开：

- 身份。
- 会员。
- 学习。
- 对话。

默认折叠但可一键展开：

- 钱包。
- 充值。
- 反馈。
- 运营。
- 审计。

必须展示：

- 身份：手机号、微信绑定、真实会员状态、来源。
- 会员：tier、套餐、到期、权益、自动续费状态。
- 钱包：余额、近 10 条流水、异常提示。
- 充值：订单摘要、充值总额、退款/补偿。
- 学习：最近学习、错题、薄弱点、掌握度、复习进度。
- 对话：最近会话摘要、风险、反馈、成本。
- 反馈：AI 反馈、运营反馈、内测反馈、教研反馈。
- 运营：备注、跟进结果、下一次跟进时间。
- 审计：最近后台动作。

对话全文默认不展示。点击展开全文时：

- 先记录 `conversation_view` 审计。
- 脱敏手机号、token、内部标识。
- 操作人必须选择查看原因：客服投诉、运营跟进、教研复核、工程排障、财务核对、其他。
- 支持复制摘要，不默认复制全文。
- 提供返回上一个会员和最近打开会员历史，支持连续处理风险队列。

### 6.4 商品账务

目标：把套餐、权益、充值、钱包、订单和异常账务分清楚。

子区：

1. `套餐权益`
2. `充值订单`
3. `钱包流水`
4. `对账视图`

`账务异常` 不做普通 tab，固定为商品账务顶部红色行动条和右侧队列；点击后按异常类型、影响金额、影响会员数和可信等级下钻。

#### 套餐权益

P0 只读或草稿配置，P1 再开放生产编辑。

字段：

- 套餐 ID
- 名称
- 价格
- 有效期
- 点数
- AI 对话权益
- 深度批改权益
- 学习报告权益
- 错题本权益
- 专属服务权益
- 可见人群
- 状态：草稿、上架、下架、归档
- 版本号
- 最近修改人

关键规则：

- 修改套餐不能影响历史订单。
- 订单必须绑定购买时的套餐快照。
- 生产上架必须二次确认并写审计。
- 灰度套餐必须明确可见人群。

#### 充值订单

订单记录和钱包流水必须分开。

订单字段：

- order_id
- user_id
- 手机号
- 套餐 / 商品
- 金额
- 渠道
- 支付状态
- 支付时间
- 退款状态
- 发票状态
- 关联钱包流水
- 异常标记

财务常用维度：

- 自然月。
- 支付渠道。
- 套餐 / 商品。
- 发票状态。
- 退款状态。

#### 钱包流水

流水字段：

- ledger_id
- user_id
- 类型：充值、AI 消耗、人工补偿、退款扣减、活动赠送、系统调整
- 点数变化
- 余额快照
- 关联 order_id / turn_id / admin_action_id
- 操作人
- 创建时间

单会员超过 500 条流水时，默认按月折叠；不得一次性渲染完整流水。

#### 账务异常

异常队列必须由明确规则生成，不能只靠前端拼列表。Batch 0 需要输出每条规则的 SQL / service 入口、运行频率和 owner。

P0 异常类型：

- 已支付未入账。
- 重复入账。
- 退款未扣权益。
- 余额为负。
- 人工补偿无原因。
- 订单有金额但无会员权益变更。
- 高成本会员无对应付费或权益。

P0 可以先只读展示异常，P1 再允许处理。

处理动作开放条件：

- 每条异常有 `detected_rule_id`、检测时间、影响金额、影响会员、可信等级。
- 异常处理写 audit。
- 处理请求带 `idempotency_key` 和对象 `version`。
- 危险处理动作提供 5 分钟 Undo。

### 6.5 反馈中心

目标：按问题分类处理“会员为什么满意或不满意，AI、教研、运营、工程哪里需要改”。

反馈统一聚合，但不统一写入一个新事实源。

反馈类型：

| 类型 | 来源 | 处理 owner | 典型动作 |
| --- | --- | --- | --- |
| AI 消息反馈 | 点赞/点踩/原因标签 | 产品 / 工程 / 教研 | 标记模型问题、知识问题、体验问题 |
| 运营反馈 | 备注和跟进结果 | 运营 | 记录联系结果、续费意向、投诉 |
| 内测反馈 | invite-test / 调研 | 增长 / 产品 | 进入内测跟进、产品需求 |
| 教研反馈 | 题目、解析、知识点 | 教研 | 修题、补证据、调整 rubric |
| 系统质量反馈 | 失败回合、慢请求、异常 | 工程 | 进入质量队列 |

布局：

- 顶部：反馈总量、待 triage、SLA 风险、owner 分布。
- 左侧：owner / 类型 / 状态分组。
- 中间：反馈队列，P0 默认只展示 `AI 消息反馈`。
- 右侧：反馈详情、关联会员、关联对话摘要、关联题目或订单、处理历史。

P0 只做：

- AI 消息反馈队列。
- owner 分组。
- open / triaged / ignored 三态。
- 关联会员和对话摘要。
- 写入处理结果和 audit。

P1 再做：

- 运营反馈、内测反馈、教研反馈、系统质量反馈完整接入。
- SLA 告警。
- 从反馈创建任务。
- 跨 owner 协作和团队视图。

每条反馈必须有：

- 来源。
- 会员或匿名对象。
- 关联会话 / 消息 / 题目 / 订单。
- 状态：open、triaged、in_progress、resolved、ignored。
- owner。
- 处理结果。
- 更新时间。
- SLA 口径：P0 只展示目标时间，P1 再做强告警。

### 6.6 系统运维

目标：把成本质量、数据可信、权限、操作审计和上线风险变成管理面，而不是散落在工程日志里。

子区：

- 成本质量：业务向，老板和财务能看懂。
- 数据可信：所有关键指标的口径、owner、等级和降级来源。
- 操作审计：所有敏感查看、导出和写操作。
- 权限审计：谁能看、谁能导出、谁能改。
- 上线面板：release / launch readiness。

成本质量必须支持：

- 总成本。
- 单有效学习成本。
- 单付费会员成本。
- 高成本低效果会员样本。
- capability 成本。
- 模型成本。
- 失败回合成本。

数据可信必须展示：

- 指标 ID。
- 定义。
- authority。
- owner。
- 可信等级 A/B/C/D。
- 更新时间。
- 降级来源。
- 样本量。

操作审计必须覆盖：

- 查看完整聊天。
- 修改会员。
- 开通 / 续期 / 撤销。
- 补点数。
- 套餐上下架。
- 订单异常处理。
- 反馈状态变更。
- 导出数据。

操作审计筛选必须支持：

- 按操作人。
- 按目标会员。
- 按时间。
- 按动作类型。
- 按敏感级别。

## 7. UI/UX 设计系统要求

### 7.1 风格

采用“专业 SaaS / CRM 后台”方向：

- 中性底色：白、灰、墨色为主体。
- 品牌强调：铜橙只用于重点按钮、活跃状态和品牌识别。
- 功能色：增长绿、风险红、警告琥珀、信息蓝。
- 不使用大面积渐变。
- 不使用装饰性 Hero。
- 不做卡片套卡片。

### 7.2 密度

不同区域采用不同信息密度：

| 区域 | 密度 | 原则 |
| --- | --- | --- |
| 经营总览 | 中密 | 少指标，高决策力 |
| 会员运营 | 高密 | 表格和筛选优先 |
| 学员 360 | 中高密 | 摘要优先，证据折叠 |
| 商品账务 | 高密 | 金额、状态、异常一眼可扫 |
| 反馈中心 | 中高密 | 摘要、owner、SLA、处理状态优先 |
| 系统运维 | 高密 | 可追溯、可筛选、可导出 |

### 7.3 组件规范

Batch 1 只建设 7 个核心组件：

- `BiAppShell`
- `BiTopBar`
- `BiSideNav`
- `BiDataTable`
- `BiSidePanel`
- `BiStatusPill`
- `BiMoneyCell`

`BiDataTable` 必须从第一版支持：

- cursor 分页。
- 排序。
- 常用筛选和高级筛选插槽。
- 虚拟滚动。
- 列显示设置。
- 空状态、筛选无结果、API 错误、数据延迟四类状态。

按 Batch 需要再建设：

- `BiMetricStrip`
- `BiActionQueue`
- `BiFilterBar`
- `BiSavedViews`
- `BiAuditDrawer`
- `BiTrustBadge`
- `BiConversationPreview`
- `BiFeedbackThread`
- `BiPackageMatrix`
- `BiLedgerTimeline`

### 7.4 数据量、输入和导出

- 5 万会员表必须虚拟滚动 + cursor 分页，首屏最多渲染 50 行。
- 搜索 input 必须正确处理中文输入法：`compositionstart` 到 `compositionend` 期间不触发查询。
- 全局搜索支持手机号、user_id、订单号；拼音首字母搜索作为 P1。
- 小数据导出可同步下载；大数据导出必须走异步任务、通知、限频、脱敏和 audit。
- 暗色模式 P1 支持，但 token 从 P0 就按可主题切换设计。

### 7.5 可访问性和交互

- 所有按钮最小点击区域 44px。
- icon-only 按钮必须有 aria-label。
- 表格支持键盘 tab 顺序。
- 危险动作必须二次确认。
- 危险动作必须支持 5 分钟 Undo，除非后端 authority 明确不可逆。
- 异步动作必须有 loading、success、error、retry。
- 筛选变化不能导致整页跳动。
- 右侧抽屉打开后焦点必须进入抽屉。
- Esc 可关闭抽屉或弹窗。
- 颜色不能作为唯一信息表达。

### 7.6 响应式

桌面是主工作面，移动端只保证查看和轻处理。

桌面：

- `1440x900` 必须完整可用。
- 会员运营默认左右分栏。
- 表格横向信息通过列控制和密度处理，不靠页面横向滚动。

iPad 横屏：

- `1024x768` 必须可用。
- 侧边导航可压缩为 icon rail。
- 学员 360 使用右侧抽屉，不打开新页面。

移动：

- `375x812` 不允许横向滚动。
- 一级导航折叠。
- 表格转为列表摘要。
- 保留标记已联系、添加备注、加入跟进队列等轻动作。
- 隐藏撤销会员、补点数、异常处理等高风险动作。
- 学员 360 全屏 sheet。

## 8. 分阶段实施计划

所有 Batch 共同门槛：

- 必须有独立 feature flag。
- 必须写 1 秒回滚 runbook，并在本地或 staging 演练一次。
- 不允许新建聊天 WebSocket 或绕开 `/api/v1/ws`。
- 不允许 BI 前端成为会员、钱包、学习事实或反馈的写入 authority。
- 每批完成后必须跑对应测试和至少一次浏览器视觉 smoke。

### Batch 0：Authority Audit 与 UI 原型

目标：先证明数据真相在哪里，再画页面。

Feature flag：无产品开关；只允许文档、审计脚本、静态原型或 `/bi-vnext` 临时原型。

任务：

- 盘点套餐 catalog、订单、充值、钱包流水、权益变更的真实来源。
- 盘点 AI 反馈、运营反馈、内测反馈、教研反馈、系统质量反馈的真实来源。
- 盘点会员对话摘要、全文、审计能力。
- 输出字段矩阵：字段、authority、可信等级、是否 P0 可用。
- 输出账务异常检测规则草案：`detected_rule_id`、SQL / service 入口、运行频率、owner。
- 验证 5 万会员查询风险：对 14 维筛选做 `EXPLAIN ANALYZE` 或可替代样本压测。
- 验证历史对话全文搜索和单会员最大消息量。
- 生成 `/bi-vnext` 或静态原型，覆盖最终 5 主区。
- 通过桌面、iPad 横屏和移动截图评审。

验收：

- 不确定项都有验证命令、代码入口或降级方案。
- 设计原型覆盖 5 个主区。
- 明确哪些模块 P0 只读、哪些 P1 才能写。
- 账务异常、反馈来源、对话全文访问都有 authority 和 owner。

### Batch 1：后台 shell、设计系统与总览静态原型

目标：让老板和运营先看到正确的信息架构、密度和交互方向。

Feature flag：`BI_BACKOFFICE_V2_SHELL_ENABLED`

任务：

- 拆分 `BiPageClient.tsx` 职责。
- 新建 BI shell、侧边导航、顶部控制条。
- 顶部加入全局手机号 / user_id / 订单号搜索入口。
- 建立 tokens：色彩、字号、间距、状态、阴影、圆角。
- 只落 7 个核心组件：`BiAppShell`、`BiTopBar`、`BiSideNav`、`BiDataTable`、`BiSidePanel`、`BiStatusPill`、`BiMoneyCell`。
- 做经营总览静态原型：KPI、WoW / MoM、行动队列、趋势图、数据可信提示。
- 保留旧 `/bi` 功能入口，避免一次性断流。
- 写 rollback runbook：关闭 flag 后回到旧 `/bi`。

验收：

- 页面从展示型看板变为专业后台。
- 不改后端功能。
- Playwright 覆盖 `1440x900`、`1024x768`、`375x812`。
- 关闭 `BI_BACKOFFICE_V2_SHELL_ENABLED` 后旧入口可用。

### Batch 2：会员运营 CRM

目标：先把最常用的运营工作流交付。

Feature flag：`BI_CRM_V2_ENABLED`

任务：

- 高密会员表格。
- 默认 7 列 + 列设置。
- 常用 5 筛选 + 高级筛选折叠。
- P0 私有保存视图。
- 风险队列 handoff。
- 学员 360 抽屉。
- 对话回顾抽屉。
- 全局搜索命中后打开学员 360。
- 备注和跟进结果。
- 低风险批量动作。
- 批量选择数量反馈和危险动作禁用阈值。

验收：

- 从老板首页点击风险项进入筛选后的会员列表。
- 点击会员打开学员 360。
- 运营动作写 audit。
- 对话全文查看必须选择原因并写 audit。
- 5 万会员首屏表格不一次性全量渲染。

### Batch 3：经营总览接真实数据

目标：让老板首页早于账务和反馈大模块上线，形成真实反馈循环。

Feature flag：`BI_OVERVIEW_V2_ENABLED`

任务：

- 接入真实 KPI 和 `metric_id` 定义。
- KPI hover 展示口径、authority、owner、可信等级。
- 今日行动队列接会员风险、账务异常、反馈风险。
- 趋势图接真实收入、活跃、学习成功和成本数据。
- 数据可信提示接 A/B/C/D 等级。

验收：

- 老板首页 30 秒内能决定今日 priority 前 3 项。
- 每个行动项都可下钻。
- C/D 可信指标不伪装成 A/B。
- overview API p95 不被 `get_member_360()` 级重查询拖慢。

### Batch 4：商品账务只读中心

目标：把套餐、充值、钱包、订单、权益变更先看清。

Feature flag：`BI_COMMERCE_V2_ENABLED`

任务：

- 套餐权益只读列表。
- 充值订单列表。
- 钱包流水 timeline。
- 订单 / 钱包 detail row 展示权益变更。
- 账务异常顶部行动条和右侧队列。
- 自然月、支付渠道、发票状态筛选。
- 学员 360 中展示账务摘要。

验收：

- 充值记录和钱包流水分开。
- 订单可跳会员。
- 异常可进入处理队列，但 P0 不做复杂处理。
- 异常都有检测规则、owner 和可信等级。

### Batch 5：对话回顾与反馈中心

目标：把“为什么”从会员对话和反馈中拉出来，但不制造第二套反馈真相。

Feature flag：`BI_FEEDBACK_V2_ENABLED`

任务：

- 会员运营中完善对话回顾：待处理 / 全部。
- 审计后查看全文，必须选择原因。
- 反馈中心 P0 接 `AI 消息反馈`。
- owner 分组。
- open / triaged / ignored 三态。
- 反馈处理结果写 audit。
- P1 再接运营反馈、内测反馈、教研反馈、系统质量反馈。

验收：

- 对话全文不默认暴露。
- 查看全文有审计。
- 反馈有类型、来源、owner、状态、处理结果和 SLA 目标。

### Batch 6：系统运维、审计与权限收口

目标：让系统可追责、可导出、可上线。

Feature flag：`BI_SYSTEM_OPS_V2_ENABLED`

任务：

- 成本质量中心。
- 数据可信中心。
- 操作审计。
- 权限审计。
- 导出审计。
- 上线面板整合。
- 大数据导出异步任务、脱敏、限频和 audit。

验收：

- 所有敏感动作有审计。
- 导出行为有审计。
- 成本估算和账单对账区分可信等级。
- 操作审计支持操作人、目标会员、时间、动作类型和敏感级别筛选。

## 9. 不确定性、验证与替代方案

| 不确定性 | 风险 | 验证方式 | 替代方案 |
| --- | --- | --- | --- |
| 套餐 catalog 是否已有稳定表 | 贸然做编辑会破坏权益 | 查 `member_console`、wallet docs、Supabase schema、旧 FastAPI 对应表 | P0 做只读套餐视图，P1 再建编辑流 |
| 充值订单来源是否统一 | 订单和钱包对不上 | 对 `/api/v1/billing/wallet`、wallet ledger、支付记录做样本对账 | P0 只展示订单/流水并列，不做自动修复 |
| 退款和人工补偿是否有规范 | 容易账务失真 | 查 ledger type、审计记录、人工补点入口 | P0 异常队列只读，P1 加处理工作流 |
| 多反馈模块是否有 canonical owner | 聚合后来源丢失 | 列出 AI feedback、invite-test、member notes、quality events | 做 feedback registry，不新建单表吞并 |
| 对话全文是否可被后台查看 | 隐私和合规风险 | 查现有 `recordMemberConversationView`、审计、脱敏 | 摘要优先，全文按权限和审计加载 |
| 成本是否能按会员归因 | 单会员 ROI 可能误算 | 对 Langfuse / session / turn / member identity 关联抽样 | 标 C 级可信，只做提示不做财务判断 |
| 移动端是否要支持复杂后台操作 | 移动表格体验差 | 访谈实际运营使用设备 | 移动只读和轻处理，批量操作限桌面 |
| 5 万会员表 SQL 性能 | 高维筛选导致页面不可用 | `EXPLAIN ANALYZE` 常用筛选 + 14 维组合查询，实际抽样 1 万行以上 | 超 200ms 上物化视图；仍不达标再评估 Elasticsearch / Meilisearch |
| 历史对话存储量级与全文搜索能力 | 对话回顾和审计加载过慢 | 查 session store 现状、单会员最大消息数、全文检索能力 | 摘要优先；全文按需分页；超阈值用 PostgreSQL FTS 或专用搜索 |
| 多设备 user_id 归一是否已有 identity service | 同一人多账号导致运营误判 | 查 auth、wechat binding、member console identity 规则 | P0 只提示 `merge candidate`，P1 再做 identity merge job |

## 10. 非目标

本计划明确不做：

- 不重写支付系统。
- 不创建第二套钱包 ledger。
- 不创建第二套会员状态。
- 不创建第二套聊天记录。
- 不新增 `/api/v1/mobile/tutorbot/ws/...` 或任何聊天专用 WebSocket。
- 不把 BI 前端变成业务写入 authority。
- 不把所有反馈混成一个来源不明的大表。
- 不为了 UI 高级感牺牲数据可信和审计。

## 11. 成功指标

上线 gate 只看 5 个核心指标：

1. 老板首页 30 秒内能决定今日 priority 前 3 项，人工 / 录屏验证通过。
2. 运营从风险队列进入处理动作的点击深度小于等于 2。
3. 会员详情打开 p95 小于 1.5s。
4. 对话全文查看 100% 有 audit + 查看原因。
5. 会员动作审计覆盖率 100%。

运维 dashboard 继续跟踪但不作为首版上线 gate：

- 充值订单和钱包流水异常可见率。
- 高风险会员队列每日处理完成率。
- 反馈从 open 到 triaged 的时间。
- BI 页面桌面、iPad 和移动视觉 smoke。
- `/bi` bundle route budget；如超过，必须拆 chunk。
- 回滚演练耗时。

## 12. 当前条件下的推荐 P0 切片

如果只能先做一版，P0 应该只做：

1. Feature flag 框架 + 1 秒回滚 runbook + 回滚演练。
2. 新后台 shell、侧边导航、顶部控制条和全局手机号 / user_id / 订单号搜索。
3. 经营总览静态原型，随后接真实 KPI、行动队列和可信等级。
4. 会员运营高密表格：默认 7 列、常用筛选、高级筛选折叠、私有保存视图。
5. 学员 360 抽屉：身份、会员、学习、对话默认展开，钱包、充值、反馈、审计折叠。
6. 充值订单 / 钱包流水只读摘要，账务异常只读行动条。
7. 对话摘要 + 选择原因后审计查看全文。
8. AI 消息反馈只读 / triage 中心；其他反馈类型 P1 增量接入。
9. 低风险运营动作：标记已联系、加备注、加入跟进队列。
10. 关键动作审计、导出审计和浏览器真实 admin session smoke。

先不要做：

- 套餐生产编辑。
- 自动退款处理。
- 批量补点数。
- 复杂权限矩阵。
- 自动营销工作流。
- 重型数仓。
- 全量反馈聚合和跨 owner 协作。
- 暗色模式完整实现。
- 多设备账号自动合并。

这能最快把运营、增长、成本、会员管理的真实闭环跑起来，同时避免账务和 authority 风险。
