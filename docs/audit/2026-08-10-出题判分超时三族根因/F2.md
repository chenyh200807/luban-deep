## 2. one business fact

> **助教在对话里向学员出示过的题组,是一等可回指对象**:唯一 object_id、`question_set` 含 items[](每项题干+选项+答案),在出示它的那一轮由**唯一 writer(turn_runtime 轮末持久化点)**写入 active_object;此后任意轮的「第N题 / 第二题答案」指代,由**唯一 ordinal resolver**(`requested_question_item_index`,deeptutor/services/question_turn_policy.py:316)对该对象解析;判分/给答案的内容真值 = 该对象 items[n],不是 history 文本的再理解。

该事实的基础设施**全部已存在**(builder=`build_active_object_from_question_context`、持久化=turn_runtime、resolver=`requested_question_item_index`、低信息闸逃生口=task#14 Layer2)——F2 不缺任何新件,缺的是**出题的那条路径没把产出喂给这套已有权威**(dormant authority + unconsumed island 成对出现)。

## 4. 路由判定:为什么这轮 capability=tutorbot、scene=None

1. `semantic_router_mode="question_lifecycle"`,mode_reason=`blocked_low_information_exam_query`:lifecycle 场景推导闸(question_lifecycle_skills.py:379-390)返回 needs_clarification。
2. orchestrator.py:444-453:`lifecycle_decision.needs_clarification` → `self._default_chat_capability(context)` = **tutorbot**,并把 business_gate_result 写进 mode_reason。
3. tutorbot.py:442-452 按 `exact_question_blocked_reason` 直接出模板终结。
4. 「为什么不回题组上下文」:不存在题组对象可回(断点①);唯一能对 history 做语义承接的主 LLM 被断点④挡在门外;唯一看过 history 的 LLM(scene proposal)被断点③剥夺决策权。**三层各自把"回去"的路堵死。**

## 6. 收权式 collapse 设计(最小,减 decider,不加新层)

### 6a. 撤销确定性闸的终局权(治断点③+④,救 F2 拒答)
- **删**:tutorbot.py:442-452 的「clarification 非空 → emit → return」终局短路;orchestrator.py:444-453 的 needs_clarification 分支不再改选 capability,只把 gate 结果写 metadata。
- **改**:needs_clarification 一律 **fall-through 到 tutorbot 主 LLM**(它已带 session_history,trace 证明预算已分配),lifecycle gate 结果降级为 prompt 内提示(「若 history 中无该题,请让学员补题干」),模板文案整段退役。
- 依据:全局律「确定性闸只做高置信快路径,一切不确定 fall-through 主 LLM,绝不模板兜底」;84d1efc58 已在 deep_question 侧做过同款撤除,这是把同一裁决补到 tutorbot 侧,**decider −1(模板短路消失),不加任何新层**。
- 附带:断点③自动消解——闸不再有否决权,`llm_scene_candidate` 从观赏字段回归决策输入(或直接删掉这次 LLM 调用省一跳,scene 交主 LLM 语义承接)。

### 6b. 题组注册收口到轮末唯一汇点(治断点①,救 F1 误判 + 给 task#14 逃生口通电)
- 现状是 3 份镜像注册逻辑(tutorbot.py:809-887 / deep_question 结构化产线 / followup 产线缺失)。**收成 1 份**:把「result 可见文本/presentation 含新题组 → 经唯一 builder `build_active_object_from_question_context` 注册」这一步,从 per-capability 上移到**轮末唯一持久化点**(turn_runtime.py:6945 一带,本就是 object-continuity 单一权威注释所在),tutorbot 里那份 camp-1 注册逻辑随之下沉删除。
- 效果:任何产线(含未来新增)出的题自动进对象;`requested_question_item_index` + task#14 Layer2 逃生口(question_lifecycle_skills.py:801-828)**不改一行即恢复生效**——连接已有件,典型 dormant-authority 接通,不是新建治理。
- 注册题面 ≠ 判分权威(tutorbot.py:829-834 已声明的边界保持):分值仍只走鲁班 V1 / rubric / open-world 裁决。
- 断点⓪ 的「解析」否定盲区(semantic_router.py:1125-1126)**不建议再堆 regex**——6b 落地后误路由只影响体验路径不再丢对象;若要修,是把 explainer-marker 判定交给已有 followup 分类器 LLM 的语义,不是给 marker 加否定词表(那是第 N+1 把尺)。

### 6c. 附带清理
- 澄清对象 `question_lifecycle_clarification` 不再写 active_object(断链轮把它写成 active_object、真题压栈,是 mirror-state 增殖;6a 落地后此对象整个退役)。
- 调用③把模板碎片当 evidence 喂考点分类器:6a 后模板消失自动消解;此形态记入 absorbing-state 巡检清单。

## 7. 能力 vs 架构判定

**架构病,非能力病。** 证据:
1. 全链最便宜的 deepseek-v4-flash 在场景建议器角色里,凭 history 一次判对(mcq_grading 0.95,理由完整复述了三题时间线)——**语义理解在系统里已经发生了,是架构把它丢弃的**(question_lifecycle_skills.py:379-390)。
2. 主 LLM 的 history 预算(1700 tokens 含三道题)已分配,只是没人让它跑(tutorbot.py:442-452)。
3. 也不是「内容真相病」:题干、选项、正确答案生成时都在 history 里,系统并不缺内容,缺的是把内容变成一等对象的那一跳(deep_question.py:5962-5966)。
4. 唯一接近「能力」的环节是 FollowupAgent 在讲解器角色里顺从用户出了题(越权产内容)——但那是断点⓪误路由送它进错门的结果,且即便如此,只要 6b 的单一注册汇点存在,产出照样被接住。

**修复优先序**:6b(对象注册收口,救 F1+F2 的根)→ 6a(闸撤权 fall-through,救所有同族罐头拒答)→ 6c 清理。6a/6b 相互独立可分 PR,均为减法(decider 3→1、模板路径 −1),零新概念、零新状态、零新旁路。
