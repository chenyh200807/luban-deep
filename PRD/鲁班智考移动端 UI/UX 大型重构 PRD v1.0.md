根据 2026-06-11 你上传的鲁班系统技术介绍、两份产品研究报告，以及我打开你当前 GitHub 仓库看到的 DeepTutor / 鲁班项目说明来定稿：这次重构不能只是“改几个页面”，而应该是一次 产品主链路重构 + 移动端 UI/UX 重构 + 学习证据可视化重构。

先把你纠正的点定死：

“100 知识点地图”以后不要再理解成具体 100 个知识点。
它只是泛指：鲁班后台有一个有限、可治理、可标注、可调度的“知识地图 / 高频母题图谱 / 采分点图谱”。
前台不卖“100 个知识点通关”，前台只卖：今天最该练什么、这题为什么丢分、下一题怎么补回来。

你项目 README 当前也明确写着，DeepTutor 是鲁班智考背后的 agent-native learning engine，产品目标不是通用聊天机器人或普通题库，而是把每次练习变成“评分、诊断真实错误、保留学习信号、推荐下一步训练”的闭环；README 还把当前最重要产品循环定义为 assess -> grade -> remember -> train -> retest。 ￼ 你上传的系统技术介绍也同样把鲁班主链路描述为“测/练/答 → 评分与诊断 → Learning Brain 长期画像 → 个性化下一步训练 → 复测验证变化”。 ￼

1. 项目名称

鲁班智考移动端学习闭环重构项目

内部代号建议：

Project Scoring Loop / 采分闭环重构

不要叫“UI 改版”。
这个项目的本质不是视觉升级，而是：

把鲁班从“能问、能批、能练”的功能集合，重构为“今日任务驱动的案例题提分系统”。

2. 一句话总目标

2.1 最终产品状态

用户打开鲁班后，不再看到一个功能大厅，也不是一个空白聊天框，而是看到：

今天最该完成的一件事
为什么推荐这件事
预计几分钟
做完后能补哪类分
开始训练

用户完成一道案例训练后，不只是看到答案，而是看到：

我写了什么
命中了哪些采分点
漏掉哪些采分点
为什么漏
怎么改写能多拿分
下一题该练什么
这个错误是否进入错题本和后续任务

系统完成一次闭环后，不只是存历史记录，而是：

把本次作答结果变成 learning_evidence
更新错因
更新母题掌握状态
更新今日任务
安排复测

⸻

2.2 最终产品定义

鲁班智考是一建建筑实务 AI 采分点诊断与案例题提分系统。
它以前台“今日任务”为入口，以后台“知识地图 / 高频母题 / 采分点 / 错因 / 学习证据”为调度系统，以“案例题渐进作答 + AI 采分点批改 + 二次作答 + 错因复练”为核心闭环。

⸻

3. 这次重构的战略判断

3.1 不做聊天框首页

不采用：

你好，我是鲁班，请输入你的问题……

原因：

* 聊天适合即时救火；
* 但不能保证学习覆盖；
* 一建实务的很多弱点是用户自己不知道该问的；
* 聊天会让产品滑向“搜答案工具”。

你的研究报告也已经明确：鲁班应采用“混合自适应”作为主产品策略，但 UI 上必须表现为“今日任务驱动”，而不是“知识点目录驱动”或“聊天驱动”。 ￼

⸻

3.2 不做教材目录首页

不采用：

建筑工程技术
项目施工管理
法规与标准
历年真题
章节练习
模拟考试

原因：

* 用户不是来逛教材；
* 章节目录不能告诉用户“今天该干什么”；
* 成人考证用户时间少，决策成本高；
* 教材目录对零基础用户太重，对老考生太低效。

正确做法：

后台知识地图化
前台任务化

研究报告也说得很直接：后台用结构化知识图谱和采分点体系驱动，前台只显示任务、风险、下一步。 ￼

⸻

3.3 不做纯 OCR 批改工具

不采用：

拍照上传
OCR
AI 批改
结束

原因：

* OCR 成本高；
* 手写识别不稳定；
* 校对负担高；
* 高频使用会拖垮体验和毛利；
* OCR 只是输入层，不是产品价值本身。

系统技术介绍里也明确，Photo Answer 只是纸面答案进入既有批改链路的输入层，confirmed_text 才是唯一送批改答案文本，raw OCR 只是证据附件。 ￼

⸻

3.4 不做纯题库

不采用：

刷题
看答案
收藏错题
继续刷

原因：

* 传统题库对客观题还能用；
* 但对实务案例题天然失灵；
* 标准答案不能告诉用户“为什么这句话不得分”；
* 用户核心痛点是“看答案会，自己写不会”。

UI/UX 研究报告中也明确指出，一建建筑实务产品核心不应是“刷更多题”，而应是“让用户知道自己为什么丢分”。 ￼

⸻

4. 重构总原则

原则 1：所有页面服务一个主循环

今日任务
→ 案例训练
→ 采分点批改
→ 二次作答
→ 错因复练
→ 下一任务

任何功能如果不能进入这个循环，就不是 P0。

⸻

原则 2：前台只给下一步，不展示复杂系统

用户不需要知道：

Learning Brain
RAG
GBrain
rubric_grader
canonical learner truth

用户只需要知道：

今天该练什么
这题哪里丢分
下一题怎么补

⸻

原则 3：案例题训练要移动端友好

手机端不能强迫用户长篇打字。

默认输入顺序：

轻练：选择 / 排序 / 匹配 / 填空
半写：句子拼装 / 短句补全
实战：手写拍照 / OCR 校对

⸻

原则 4：批改先诊断，再证据，再答案

批改结果页顺序必须是：

分数区间 + 置信度
最该改的 3 个问题
采分点证据链
改写建议
二次作答
标准答案折叠
下一题推荐

研究报告中对 AI 批改页的要求也非常明确：第一屏先给分数区间和置信度，紧接着给“最该改的 3 个问题”，第三层才是证据链，标准答案默认折叠。 ￼

⸻

原则 5：错题本不是错题仓库，而是错误模式库

错题本要回答：

我持续以什么方式丢分？

不是：

我做错过哪些题？

⸻

原则 6：AI 提问必须导回训练

AI 答疑不是主链路。

所有答疑结束后，都要有：

练一道同类题
加入今日任务
进入错因复练
拍照批改这题

⸻

原则 7：前端不能自作聪明

前端不得自己推断：

分数
掌握度
下一任务
正式评分
长期学习画像

这些都必须来自后端 read model 或受控服务。

系统技术介绍里已经把边界讲得很清楚：RAG 只提供 retrieval / context / source expansion，不判分；LearnerStateService 是统一长期 learner truth service；Learning Report read model 是唯一 producer，前端不应该自行重组 mastery 或 textbook progress。 ￼

⸻

7. 核心用户路径

7.1 新用户首次激活路径

目标

3 分钟内让用户体验到鲁班核心价值：

我知道你案例题为什么丢分。

流程

打开小程序
→ 选择考试专业：一建建筑实务
→ 选择剩余备考状态：今年考 / 明年考 / 只差实务
→ 选择每天可用时间：5 / 15 / 30 / 60 分钟
→ 做 1 道轻练诊断题
→ 进入半写 1 小问
→ 输出首次诊断卡
→ 生成今日任务

首次诊断不要做什么

不要一上来要求：

注册完整资料
绑定手机号
购买会员
填写长问卷
上传整套试卷

⸻

7.2 老用户每日学习路径

打开今日页
→ 查看今日主任务
→ 选择开始
→ 进入半写训练
→ 完成采分点选择 / 答案拼装 / 短句补全
→ 查看 AI 诊断
→ 再答一次或练同类题
→ 自动更新错题本和明日任务

⸻

7.3 拍照批改路径

AI 批改 Tab / 今日任务 / 题目详情
→ 选择题目
→ 拍照上传手写答案
→ 图片质量检测
→ OCR 识别
→ 黄色低置信片段校对
→ 确认文本
→ 批改
→ 采分点证据链
→ 二次作答
→ 加入错题本
→ 推荐同类题

⸻

7.4 错因复练路径

错题页
→ 选择“关键词缺失”错因
→ 查看关联母题和采分点
→ 重做一道同类题
→ 系统对比上次是否改善
→ 如果改善，降低该错因风险
→ 如果未改善，安排复测

⸻

7.5 AI 提问路径

用户在任意页面点击“问鲁班”
→ 系统带入当前题目 / 当前错因 / 当前母题上下文
→ 回答问题
→ 给出后续动作：
   练一道同类题
   加入今日任务
   进入半写训练
   拍照批改

8.6 今日页状态

状态 A：新用户无数据

先做 1 道小诊断，我告诉你案例题最容易丢分在哪里。
按钮：开始 3 分钟诊断

状态 B：正常用户

展示今日主任务。

状态 C：用户断更

这几天没学也没关系，计划已按剩余时间重排。
今天先做 1 道最值钱的题。

状态 D：考前冲刺

距离考试还有 14 天。
现在不建议全书乱刷，先补这 3 类高频失分点。

状态 E：批改高风险

上次批改存在较高不确定性，建议先校对答案后再复练。

26. 系统架构边界对 UI/UX 的约束

这部分是给后续 Codex / Claude Code / Hermes Agent / 工程团队看的。

26.1 不新增第二套聊天入口

稳定聊天 / 流式入口仍然是：

/api/v1/ws

README 当前也明确 /api/v1/ws 是 web、小程序、TutorBot、replay、resume 的唯一稳定 streaming/chat transport。 ￼

⸻

26.2 UI 不直接决定 capability

前端可以传：

intent

entry_flow
current_question_id

ChatOrchestrator
QuestionLifecycleDecision
CapabilityRegistry

⸻

26.3 RAG 不判分

RAG 只提供知识证据。
批改由：

construction_grading
rubric
runtime adjudicator
deterministic validator

来做。

系统技术介绍中对案例题 lane 的定义也是：case_question 由 compiled rubric + source/spec/list authority + runtime LLM adjudication 负责，deterministic validator 负责防 false-positive 和 fail-closed。 ￼

⸻

26.4 OCR raw text 不能直接送批改

必须是：

raw_ocr_text
→ 用户确认
→ confirmed_text
→ 批改

系统技术介绍的禁止模式也明确：不能让 OCR raw text 自动替代学生确认稿。 ￼

⸻

26.5 前端不能自己算 mastery

前端只能展示：

Learning Report read model
Mistake Book read model
Attempt Detail read model
Home Personalization read model

系统技术介绍中也明确，build_learning_report_read_model() 是 Learning Report 唯一 producer，read model 是只读 projection，不写持久化状态。 ￼

⸻

26.6 微信真实入口必须验证

不能只说 Web harness 通过。

必须验证：

devtools_project_root = yousenwebview
target_subpackage = packageDeeptutor
target_page = 具体页面
entry_flow = 具体动作链路
auth_state = logged_in / qa_token / auth_blocked / unknown
auth_mode = real_wechat / local_dev_wechat / manual_token / none

系统技术介绍里也要求，涉及微信体验时必须区分 wx_miniprogram、yousenwebview、yousenwebview/packageDeeptutor 和 Web shadow QA 入口。 ￼

31. 后续团队执行铁律

这次重构后，所有需求评审都问 10 个问题：

1. 它是否服务今日任务？
2. 它是否提高案例题输出能力？
3. 它是否产生采分点级证据？
4. 它是否能进入错因复练？
5. 它是否降低手机端输入负担？
6. 它是否避免高频 OCR 成本失控？
7. 它是否导向二次作答或同类题？
8. 它是否遵守现有 authority 边界？
9. 它是否能在微信真实入口验证？
10. 它是否让用户更清楚自己为什么丢分？

如果一个功能回答不了这 10 个问题，就不要进入 P0。

32. 最终方向

这次重构成功后的鲁班，应该长这样：

不是题库
不是聊天机器人
不是 OCR 工具
不是课程平台
而是：
打开就知道今天最该练什么；
练题不用在手机上打长文；
写完能看到采分点证据链；
错题不是堆题，而是错误模式；
系统会记住错误并安排复练；
复测后能看出是否真的进步。

一句话总控：

鲁班智考移动端重构的目标，是把产品从“功能集合”升级为“案例题提分闭环系统”：前台今日任务驱动，后台知识地图 / 母题 / 采分点 / 错因调度，核心交互是渐进作答，核心价值是采分点诊断，核心留存来自错因复练和复测进步。
